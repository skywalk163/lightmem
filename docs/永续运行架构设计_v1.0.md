## §0 结论摘要

**1. 目标要拆成两层，不能混为一谈。**
「进程的可持续性」与「记忆的耐久性」是两个独立失效域：进程死了用守护拉起（秒级），记忆丢了只能靠 WAL/快照（分钟级）。混在一起谈，必然做出「重启了但失忆」的假高可用。

**2. 骨架比想象中完整，但四处「声明 ≠ 接线」。**
`/healthz` 已经带存储探针（`server_metrics.go:300-326`）、整合 worker 已经有 5 分钟 ticker（`consolidate.go:48-50`）、访问计数已经有落库定时器（`main.go:172-189`）、FreeBSD rc.d 已经有 PG 就绪等待与启动后健康等待（`lims-088-rc.d/lightmem:101-112,198-210`）、ZFS 快照+send 链路已经是可复跑脚本（`scripts/zfs_backup.sh`）。**缺的不是架构，是这四处断线**（见 §2.2）。

**3. 生产机（FreeBSD 0.88）今天不具备崩溃自愈。**
rc.d 用 `daemon -f -u -P -o` 起进程（`lims-088-rc.d/lightmem:183-197`），**没有 `-r`** → 守护者只记录 pid，不重启；进程一崩就是永久宕机，直到人工 `service lightmem start`。这是 L1 层唯一真正致命的一处。

**4. 最危险的一条不在崩溃，而在「重启成功但连错了库」。**
`PGConfig.Primary / Replica / Sharding` 三个字段在 `profile.go:87-89` 有定义，**全仓零调用点**；`newPgBackend` 只读 `cfg.PG.Host`（`backend_pg.go:42-56`），而 `lims-smb.profile.yaml:17-31` 与 `lims-enterprise.profile.yaml:17-32` **都没有设 `pg.host`**（只写了 primary/replica/sharding）。同时 `docs/档位能力矩阵.md:15,29` 对外声明 SMB 是「单节点/双节点主备」「单库/主备」。→ 这两档 profile 原样启动会得到一个空 host 的 DSN（pgx 回落到本地默认），**健康检查通过、文档说主备、实际连的是本机**。

**5. 落地顺序（详见 §5）**：P0 守护（无代码改动，收益最大）→ P1 停机排水 + 健康分层（小加法）→ P2 睡眠调度器（新增文件，默认关）→ P3 存储耐久显式化 + 启动恢复自检 + 主备二选一。

| 层 | 目标命题 | 现状 | 缺口编号 |
|---|---|---|---|
| L1 进程守护 | 崩溃后自动恢复，人工介入从「必须」降为「可选」 | Linux 有 systemd 单元（`Restart=on-failure`）；FreeBSD 无自重启 | G1 G2 G13 |
| L2 健康语义 | 「活着」与「可用」可区分、可被守护层判定 | 有 Ping 探针，但无 liveness/readiness 分离，PG 缺表仍 200 | G3 G4 G11 |
| L3 睡眠整理 | 低峰整理不阻塞在线读写，停机不留半成品 | 整合有调度但无窗口/预算/排水；5 引擎无调度 | G5 G6 G7 G8 G9 |
| L4 持久与恢复 | 重启后记忆时间线可接续，RPO/RTO 分档可承诺 | WAL 开关已有；同步级别/checkpoint/恢复自检缺；主备未接线 | G10 G11 G12 G14 |

## §1 目标、口径与非目标

### 1.1 把「永续」拆成四个可证伪命题

| 命题 | 可证伪的判据（不满足即不成立） |
|---|---|
| **C1 进程可持续** | `kill -9 $(pgrep -f lightmem-kernel)` 后，无需人工介入，服务在 T 秒内监听同一端口且鉴权矩阵复验通过 |
| **C2 可用性可判定** | 存储层不可读写时，守护层能拿到**非 200**（而不是「进程在、接口全 500」） |
| **C3 记忆可维护** | 整理窗口内的在线读写 P95 与窗口外相比劣化 ≤ 20%，且窗口被中断不留不一致状态 |
| **C4 时间线可接续** | 崩溃/断电后重启，**已确认的写入**条数与重启前一致（RPO=0），且日志明确记录「从哪个状态恢复」 |

### 1.2 大脑隐喻 → 工程状态机（本设计的核心抽象）

「只有休息、没有宕机」在工程上不是一句形容词，而是一张**状态迁移表**。每一态都要回答：对外是否可用、谁触发、失败时回退到哪。

| 大脑态 | 工程态 | 触发 | 对外可用性 | 失败回退 |
|---|---|---|---|---|
| 清醒 | **Serving** | 常驻 | 读写全可用 | → 昏迷（崩溃）或 小睡（窗口到） |
| 小睡（整理记忆） | **Maintenance** | 低峰窗口 / 固定间隔 | **读写照常**；后台任务让位 | 整理失败退避，不影响 Serving |
| 深睡（固化记忆） | **Snapshot** | ZFS 定时快照 / `zfs send` | 读写照常；快照近零成本，send 需限速 | 快照失败告警，下轮重试 |
| 打盹（值守） | **Supervised** | 进程不在但守护者在 | 不可用（秒级） | 守护拉起 → Serving |
| 昏迷→苏醒 | **Recovery** | 进程意外退出 / 主机重启 | 不可用（T 秒级） | 自检 → 声明 ready → Serving |

**不变式（Invariants）**：
- I1：Serving / Maintenance / Snapshot 三态下，**API 层不得主动返回 5xx**（写排队属于可接受降级，但必须可观测）。
- I2：任何状态迁移必须**落日志 + 计数指标**；「静默降级」视为缺陷。
- I3：Recovery 态在**完成恢复自检前不得声明 ready**（否则负载均衡会把流量打到一个读不出数据的进程上）。

### 1.3 非目标（明确不做，避免范围蔓延）

- 不做跨机房双活 / 异地多活（本设计只到**主备**与**可恢复**）。
- 不引入 Kubernetes Operator、不做自动扩缩容控制器。
- **不加任何第三方依赖**（调度器用 stdlib `time`/`sync`，见 §6 红线）。
- 不改 `model.go` / `storage.go` / `lifecycle.go` / `compliance.go` 的 Schema 语义，不动 `kernel/migrations/*.sql`。
- 不做应用内自杀式自拉起（fork 自身）：不可测、易双实例抢端口（反模式，见 §3.1.4）。

### 1.4 分档可用性口径（RTO / RPO 承诺表）

> RTO = 恢复服务时间；RPO = 允许丢失的数据时间窗。**没有明确 RPO 的「高可用」是营销词。**

| 档位 | 守护手段 | RTO（目标） | RPO（目标） | 依据 |
|---|---|---|---|---|
| **Solo** | rc.d + `daemon -r`（或 cron watchdog） | ≤ 30s（自动） | **0**（SQLite WAL + `synchronous=FULL`） | 单机自愈，不做节点冗余 |
| **Family** | 同上 + PG 单库 | ≤ 60s | **0**（PG WAL 已提交事务） | PG 崩溃恢复原生能力 |
| **SMB** | PG 主备（streaming）+ 独立整理进程 | ≤ 5min（含人工确认切换，或自动切换若接线） | 0（sync）/ ≤ 秒级（async） | `profiles/lims-smb.profile.yaml:24-29` 已声明，**待接线（G12）** |
| **Enterprise** | 分片 + 多副本 + LB 探针 | 按 SLA 定 | 按 SLA 定 | `profiles/lims-enterprise.profile.yaml:21-32`，**当前为声明态** |

> ⚠️ 本表 SMB/Enterprise 两行是**目标值**，不是现状。现状见 §2.2 G12。

## §3 四层架构设计

### 3.1 L1 进程守护（Supervision）

#### 3.1.1 设计模型：三层守护，职责不重叠

```
第 1 层  init（rc.d / systemd）        —— 「开机起、关机停」+ 依赖顺序（等 PG）
第 2 层  supervisor（daemon -r / systemd Restart）—— 「崩了拉起来」+ 防抖
第 3 层  应用内自愈（Go 进程内）        —— 「不自杀」：降级服务而不是 exit
```

**边界纪律（很重要）**：
- 第 3 层**绝不**主动 `os.Exit`（除启动期 fail-fast：配置损坏、后端装配失败）——否则把可降级故障升级成重启。
- 第 2 层**只负责拉起**，不做业务判断（判断交给 L2 健康）。
- 第 1 层只管顺序与生命周期，不做重启。

#### 3.1.2 FreeBSD（生产机 0.88，当前缺失项）

**方案 A（推荐）：给现有 `daemon(8)` 加 `-r`**

```sh
# integrations/lims-088-rc.d/lightmem:183-197 的改动方向（示意，非本文件实施）
/usr/sbin/daemon -f -r -u "${lightmem_user}" -P "${pidfile}" -o "${lightmem_log}" ...
```

⚠️ **必须同时满足两个前提**，否则 `service stop` 会变成「杀一次、拉一次」的死循环：
1. **保留 `-P`（supervisor pidfile），不要用 `-p`**：FreeBSD `daemon(8)` 手册明确指出 `-P` + `-r` 才是 rc 脚本的正确组合——`-p` 给的是**子进程** pid，向它发信号会被守护者重新拉起（[daemon(8) 手册](https://www.unix.com/man-page/FreeBSD/8/daemon/)）。
2. **stop 必须先杀 supervisor**：现有 `lightmem_stop`（`lightmem:117-141`）正是「先 `pkill` 子进程 → 再 `kill -TERM $(cat pidfile)`（即 supervisor）」的顺序，与新语义**天然兼容** ✅。这一点必须在改动后**立刻复验**（验收 §7-R1）。

**方案 B（不改守护者）：cron watchdog**

```sh
# /etc/cron.d/lightmem-watchdog：每 2 分钟探一次，失败即重启，带冷却防抖
*/2 * * * * root fetch -q -T 5 -o /dev/null http://127.0.0.1:18443/healthz || \
  ( [ -f /var/run/lightmem/watchdog.cooldown ] || \
    ( touch /var/run/lightmem/watchdog.cooldown; service lightmem restart; \
      logger -t lightmem-watchdog "restart triggered" ) )
```
> 冷却文件是**必需**的：否则 `restart` 期间探针必然失败 → 每 2 分钟重启一次，把「偶发崩溃」放大成「持续抖动」。

**选型**：A 更快（秒级）但需改部署脚本 + 复验 stop 语义；B 零侵入但延迟最长 2 分钟。**建议 A，B 作为 A 的兜底**（两者可共存：watchdog 探的是 L2 的 `/readyz`，`-r` 管的是进程死亡）。

### 3.2 L2 分层健康（Health Semantics）

#### 3.2.1 三层语义（现状只有第 1.5 层）

| 层 | 问题 | 判定 | 端点 | 现状 |
|---|---|---|---|---|
| **Liveness** | 进程还活着吗？ | HTTP server 在监听 | `/healthz`（保留） | ✅ 已有 |
| **Readiness** | 现在能服务吗？ | 依赖可达 **且 记忆可读** | **`/readyz`（新增）** | ⚠️ 部分（只 Ping） |
| **Deep** | 记忆可读写吗？ | 写→读回→删 探针 | 内部脚本 / 启动自检 | ❌ 无（**刻意不放进 HTTP 高频路径**：会引入写放大） |

> **设计决定**：不为深层探针开高频 HTTP 端点。**读写探针只在启动自检与人工演练时跑**（§3.4.4），HTTP 侧最高到 readiness。

#### 3.2.2 关键修补：让 readiness 真的能判定「记忆可读」

现状 `Ping` 只证明**连接**（`backend_pg.go:79` 就是 `db.PingContext`）。空库/未应用迁移时，`memories` 表不存在 → `/healthz` 200，业务全 500。

**`/readyz` 判据（加法设计，不改既有端点语义）**：
1. `backend.Ping(ctx)`（连接层）；
2. **轻量读探针**：`SELECT 1 FROM memories LIMIT 1`（SQLite/PG 通用；空表也算通过——空表是合法状态）；
3. 探针预算 ≤ 2s（与现有 `server_metrics.go:302` 一致），**不扫全表**（避开 `backend_sqlite.go:123-144` 的全表反序列化）；
4. 任一步失败 → **503** + `{"status":"degraded","check":"..."}`。

> 实现落点建议：新增 `kernel/health_probe.go`（只增不改），在 `main.go:202-203` 的外层 mux 追加 `/readyz`——与既有 `/healthz` 同一模式，**不触碰 `kernel/router.go`**。
> **唯一非纯增量处**：`/readyz` 必须加入 `auth.go:256-273` 的运维端点豁免，否则探针 401（与 T3 实测踩过的 `/healthz` 同类问题）。这属于**同类豁免的加法**，需同步扩 `auth_test.go:685-735` 的用例集。

### 3.3 L3 睡眠整理（Maintenance Windows）

#### 3.3.1 现状再陈述（避免重复造轮子）

- **整合**：已有 ticker（`consolidate.go:264-286`），默认 5min，`LIMS_CONSOLIDATE_INTERVAL` 可覆盖（`main.go:144-151`）。
- **生命周期 5 引擎**：有触发入口（`access.go:405-469`），**无调度器**（`main.go:195-198` 只注册路由）→ **G7**。
- **访问计数落库**：有独立定时器（`main.go:172-189`），但**不参与统一停机**（G6）。

→ 所以 L3 的设计不是「把 worker cron 起来」（那已经有了），而是：**统一调度器 + 窗口/预算/退避 + 停机排水**。

#### 3.3.2 调度器设计（stdlib only）

新增 `kernel/scheduler.go`（只增不改，不引依赖）：

```go
// 概念签名（示意，非最终实现）
type MaintenanceJob struct {
    Name     string        // "consolidate" | "lifecycle:archive" | "access-flush" | ...
    Interval time.Duration // 固定间隔（与窗口二选一或叠加）
    Window   *Window       // 低峰窗口 {Start: "03:00", End: "05:00", Days: [...]}；nil = 全时段
    Budget   Budget        // {MaxItems, MaxDuration, MaxWrites}
    Backoff  Backoff       // 失败退避：1m → 2m → 4m … 封顶 30m
    Run      func(ctx context.Context) (Report, error)
}

type Scheduler struct{ /* ticker + 单飞(single-flight) + 报告落日志/指标 */ }
```

**四条硬规则**：
1. **单飞**：同一 job 的上一轮未结束，跳过本轮（写日志 `skipped: still running`），不并发堆积。
2. **预算**：每轮受 `MaxItems`/`MaxDuration` 约束，超预算**优雅让位**（记录 `budget_exhausted`，下轮从扫描顺序继续；因动作幂等（A13），不会重复破坏数据）。
3. **退避**：连续失败指数退避，封顶 30min；连续失败 ≥ N 次转**告警而非重启**（区分「数据问题」与「进程问题」）。
4. **窗口**：`Window` 非空时只在窗口内触发；窗口结束时若在跑，**让当前轮跑完**（不硬杀），但不再启动新轮。

#### 3.3.3 Solo 档的「整理不阻塞在线」方案（G8 的正面设计）

问题本质：`sqliteBackend` 用**单连接 + 全局 `mu`**，且读取是**全表 JSON 反序列化**。因此：

- ❌ 不要指望「WAL 并发读」——本后端把读也串行化了。
- ✅ 做法一（推荐，改动最小）：**分片让步**——`ScanAll` 改为按 `LIMIT/OFFSET` 或 `memory_id` 游标分页（每批 ≤ 200 条），**每批之间 `runtime.Gosched()`/`time.Sleep(1-5ms)` 主动让出 `mu`**，让在线请求插队。代价：单轮耗时变长（可在窗口内接受）。
- ✅ 做法二：整理 worker 用**独立进程**（拓扑 B 的形态，见 §4.2），彻底与在线服务解耦；Solo 档不采用（部署复杂度不划算）。
- ✅ 做法三：把「读」与「写」锁分离（`RWMutex`）——但 SQLite 单连接下写仍阻塞读，收益有限，且触碰既有并发模型（风险高）。**不推荐在 P2 做。**

**量化目标**：窗口内在线 P95 相比窗口外劣化 ≤ 20%（§7 压测判据）。

#### 3.3.4 停机排水协议（Drain，关闭 G5/G6）

把 `main.go:286-301` 的关闭序列从「尽力而为」升级为**有序排水**：

```
① server.Shutdown(ctx)            // 停止接收新请求，等在途请求（已有，:287-292）
② scheduler.Stop()                // 不再启动新轮（新增）
③ wg.Wait() with timeout          // 等整合/生命周期/落库 三类 goroutine 返回（新增；G5/G6）
④ backend 收尾：wal_checkpoint(TRUNCATE)（若启用，见 §3.4.1）
⑤ backend.Close()                 // 已有（:299-300）
⑥ 记录「未完成轮次」到日志         // 供下次排障/恢复自检读取
```

- ③ 的超时建议 = `-shutdown-timeout`（默认 10s）；超时则**记录未完成**并继续关闭（不能因后台任务阻塞停机）。
- 目前 `accessTracker.Flush` 的 goroutine 用 `context.Background()`（`main.go:178`）→ 必须改为受 `bgCtx` 约束，纳入 ② / ③。

#### 3.3.5 引擎接线矩阵（默认全关，零回归）

| 引擎/任务 | 现状触发 | 目标触发 | 默认 | 开关（新增，未设=现状） |

### 3.4 L4 持久化与恢复（Durability & Recovery）

#### 3.4.1 SQLite：把隐式默认变成显式契约（G10）

**现状**：只有 `PRAGMA journal_mode=WAL`（`backend_sqlite.go:72-77`，需 `wal_mode: true`；solo profile 已设 `lims-solo.profile.yaml:26`）。其余全靠 SQLite 默认。

**设计**（全部通过 profile 新增字段控制，**字段为空 = 完全不执行该 PRAGMA = 现状逐位一致**）：

| 新 profile 字段 | 对应 PRAGMA | 取值 | 说明 |
|---|---|---|---|
| `sqlite.synchronous` | `PRAGMA synchronous` | `full`(默认推荐) / `normal` / `off` | **耐久级别显式化**。语义（SQLite 官方口径）：`FULL` = 提交即落盘（崩溃与断电都不丢已确认写）；`NORMAL` = **应用崩溃安全**，但**断电可能回滚已确认写**；`OFF` 仅测试用 |
| `sqlite.busy_timeout_ms` | `PRAGMA busy_timeout` | 例 `5000` | 单连接下主要用于与外部工具/备份共存 |
| `sqlite.wal_autocheckpoint` | `PRAGMA wal_autocheckpoint` | 例 `1000` | 显式化自动 checkpoint 阈值 |
| `sqlite.checkpoint_on_close` | 关闭时 `PRAGMA wal_checkpoint(TRUNCATE)` | `true/false` | 关闭时把 WAL 收进主库，避免 `-wal` 残留（`Close()` `:469-473` 当前无此动作） |

**先量基线再改（必做，1 分钟）**：`modernc.org/sqlite` 的默认值继承 SQLite 上游（默认应为 `synchronous=FULL`），但**本文未在 0.88 上实测**——改配置前先在真机读出当前值，避免「以为改了、其实早就是默认」或反向的误判：

```sh
# 0.88 上（python3 随系统自带，无需装 sqlite3 CLI）；把路径换成当前实际数据文件
python3 -c "import sqlite3;c=sqlite3.connect('/usr/local/lightmem/data/lims.sqlite');\
print('journal_mode=',c.execute('pragma journal_mode').fetchone()[0]);\
print('synchronous=',c.execute('pragma synchronous').fetchone()[0]);\
print('wal_autocheckpoint=',c.execute('pragma wal_autocheckpoint').fetchone()[0])"
```

把输出记进部署记录（对应 R22），后续变更与它对比。

**口径决定（建议，需用户确认 Q1）**：
- **Solo 档默认 `synchronous=full`**，理由：记忆写入的产品承诺是「确认即不丢」，`FULL` 是唯一无需脚注的答案；单机写入量小，每提交一次 fsync 的代价可接受。
- 若压测显示写延迟不可接受（例如批量导入），再降到 `normal` 并**在文档中明确写出「断电可能丢最近若干秒已确认写」**——不允许「悄悄用 normal 却宣称不丢」。

#### 3.4.2 路径纪律（cwd 是隐形的配置项）

- `profiles/lims-solo.profile.yaml:21` 用**相对路径** `./data/lims.sqlite`，`storage.archive.path`（`:31`）亦然 → **谁启动进程决定了数据落在哪**。
- 现状 OK：rc.d 通过 `lightmem_chdir="/usr/local/lightmem"`（`lims-088-rc.d/lightmem:41`）钉住工作目录 ✅；quickstart 生成的 profile 用**绝对路径** `$RUN_DIR/data/lims.sqlite`（`install.sh:77,141`）✅。
- 风险：`install.sh:321-335` 生成的 systemd 单元**没有 `WorkingDirectory=`**——它自己的 `ExecStart` 用的是绝对 profile 路径（`:329`），所以今天没事；但一旦有人把该单元指向 `profiles/lims-solo.profile.yaml`，数据会相对 systemd 的 cwd 落盘。
- **设计决定**：① 所有 supervisor 配置显式写绝对 `chdir`/`WorkingDirectory`；② 启动日志打印**解析后的绝对数据路径**（可观测性，一行成本）。

#### 3.4.3 PostgreSQL：主备二选一（G12，必须做决策）

**不允许存在的第三种状态**：「profile 里声明了主备、文档里宣传了主备、代码里没人读」。可选路径：

| 路径 | 动作 | 成本 | 适用 |
|---|---|---|---|
| **A. 接线** | `newPgBackend` 读取 `Primary`/`Replica`；实现：① 写全部走 primary；② 读可选走 replica（需容忍复制延迟）；③ 故障转移策略（自动 or 人工提升） | 高（要写故障转移与一致性策略，且**不能**引入第三方依赖） | SMB 及以上真要「自动切换」 |
| **B. 如实降级（推荐先做）** | ① 改 `lims-smb/enterprise.profile.yaml`：补上 `pg.host`（否则**今天就连不上**）；② `validate()` 增加「pg 档必须能解析出 host」的启动期校验（fail-fast，与 `ConfigureAuth` 的 fail-fast 哲学一致）；③ 把 `primary/replica/sharding` 字段标注为「**声明态，未接线**」，同步修 `docs/档位能力矩阵.md:15,29` | 低（防错 + 文档诚实） | 立刻可用，避免「静默连本地」 |
| **C. 混合** | 先做 B（防错+诚实），再按需求把 A 拆成独立里程碑 | 低→高 | 推荐路线 |

> **B 的第①条是 P0 级修复**：即使什么都不做，也必须补 `pg.host` 或加启动校验——否则 SMB/Enterprise 档「部署成功」是假象。

**PG 侧其余口径**（引用既有结论，不重复论证）：`synchronous_commit` 与 ZFS `sync=always` 的取舍见 `lightmem.md:1201`；WAL dataset `sync=always` 见 `lightmem.md:1197`；启动时**不做自动迁移**（`kernel/migrations/*.sql` 不动是红线），改为**启动自检 + 明确报错**（见 §3.4.4）。

#### 3.4.4 启动恢复自检（Boot Report，关闭 G11）

启动序列在「装配后端之后、对外 ready 之前」插入一次自检，输出**结构化一行日志** + 供 `/healthz` 读取的内存快照：

| 检查项 | SQLite | PG | 失败处置 |
|---|---|---|---|
| 存储可达 | `Ping` | `Ping` | fail-fast（已有语义：`main.go:78-81`） |
| 表结构存在 | 自建（`backend_sqlite.go:86-92`）→ 恒过 | `SELECT 1 FROM memories LIMIT 1` | **fail-fast**（缺迁移就别对外声明 ready） |
| 数据条数 | `SELECT count(*)` | 同 | 记录（用于「重启前后对比」，R16 判据） |
| 最后 checkpoint/恢复点 | WAL 文件大小 + `PRAGMA wal_checkpoint(PASSIVE)` 返回 | PG `pg_last_xact_replay_timestamp()`（若为备库） | 记录 |
| 二进制 vs 库 | 对比 `VERSION`（`install_lims_rc_d.sh:129-134`） | 同 | 不一致 → **警告 + 继续**（记忆数据本身无版本依赖） |
| 上次异常? | 存在「未完成轮次」标记（§3.3.4 ⑥ 写入） | 同 | 记录 + 下轮整理自然收敛（A13 幂等） |

**日志范例（目标形态）**：
```
[boot] recovery report: backend=pgvector table=ok rows=12831 commit=a1b2c3d version_match=true
       last_consolidate=2026-10-19T02:10:11Z unfinished_round=none
```
> 这一步的意义就是把用户的那句话落地：**「持续存在」不只是进程的连续，而是记忆时间线的连续**——而时间线的连续必须被**打印出来**才算被证明。

#### 3.4.5 备份与恢复演练（沿用既有资产）

- 快照：`scripts/zfs_backup.sh snapshot -p zroot/lims -r -t hourly|daily|weekly`（保留 48/7/4，`prune` 只删本规范内快照，幂等）。
- 异地：`... all -d backup01:tank/lims-backup`（增量优先，无共同快照退全量）。
- 恢复：`... rollback -s zroot/lims@daily-YYYYMMDDHHMMSS`（**人工动作，不进自动链路**——脚本已如此设计）。
- RPO 换算（写给运维）：hourly → RPO ≤ 1h；daily → ≤ 24h；**PG 主库在线时 RPO=0**（WAL 已提交事务），快照只兜「误删/逻辑损坏」。
- **季度演练**：从快照恢复 → 起服务 → 跑 §3.4.4 自检 → 验证「恢复条数 + 最近整合时间」符合预期。（A10 已提供 `do_rollback` 与 `list`，演练成本低。）

#### 3.4.6 验收（L4）

| 判据 | 做法 | 期望 |
|---|---|---|
| R16 | 写 N 条 → `kill -9` → 重启 | 条数与内容**完全一致**（RPO=0）；日志出现 recovery report |
| R17 | 拔电/硬重启（若可安排） | `synchronous=full` 下 R16 同样成立；`normal` 下记录实际丢失窗口（用于校准承诺） |
| R18 | PG 指向**未应用迁移**的空库 | 启动 **fail-fast**（而非「健康但全 500」）——G3 的根治版 |
| R19 | SMB profile 原样启动 | ① 若走路径 B：启动期明确报错「pg.host 未配置」（而不是连到 localhost） |
| R20 | 每日快照存在 + 一次真实回滚恢复 | `zfs_backup.sh list` 有当日快照；回滚后自检条数 > 0 |

## §4 部署拓扑：两档，各自闭环

### 4.1 拓扑 A —— 单机自愈（Solo / 轻 Family；0.88 现状 + 增强）

```
        ┌──────────────────────────────────────────────────────┐
        │ sysinit/rc.d: lightmem_enable=YES（开机自启）          │
        │   └─ daemon -f -r -P …（异常退出自动拉起）★G1          │
        │        └─ lightmem-kernel :18443                      │
        │             ├─ /healthz  /readyz ← 探针/LB ★G3         │
        │             ├─ 后台调度器（窗口+预算）★G7               │
        │             └─ 存储：SQLite WAL(sync=full)★G10         │
        │                    └─ ZFS: zroot/lims（hourly/daily）  │
        └──────────────────────────────────────────────────────┘
                  ▲                          ▲
        cron watchdog（失败即重启，带冷却）    zfs_backup.sh send → 容灾池
```
- 定位：**不是节点冗余，而是「快速自愈 + 可恢复」**。
- 承诺：RTO ≤ 30s（自动）；RPO = 0（WAL，单机故障）；RPO ≤ 1h（快照，误删/逻辑损坏）。
- 关闭的缺口：G1 G3 G5 G6 G7 G10 G11 G13 G15。

### 4.2 拓扑 B —— 主备分离（SMB / Enterprise，目标态）

```
   Agents ──► LB（探针 /readyz）──► Gateway（无状态 ×N）──► Coordinator
                                     │                        │
                                     └────► Worker ×N（各自分区）│
                                              │                 │
                        PG 主（写）◄───────────┘                 │
                          │  streaming / sync                     │
                        PG 备（读/接管）                          │
                                                          Maintenance Worker
                                                          （独立进程/Deployment）★G8
```
- 与既有词汇表的对应：`node_role.go:23-32` 的 coordinator/worker/archive/gateway；`lightmem.md:1143-1161` 的拓扑与一致性口径。
- **关键解耦**：整理 worker 独立进程 → ① 整理崩溃不拖垮在线；② Solo 档的锁竞争问题不再存在（G8 从根上消失）；③ worker 可单独重启（「睡眠」与「存在」彻底解耦——正是用户那句话的工程形态）。
- 当前可落地程度（诚实标注）：角色为**骨架实现**（`node_role.go:101-233` 是内存版注册/广播，默认关），跨节点 rank merge 由 `features.cross_node_rank_merge` 控制（`profile.go:404-408`）→ **拓扑 B 需要先完成 G12 与角色接线**，不是配置一下就能开。

### 4.3 何时从 A 升 B（判据，避免过早复杂化）

满足**任意两条**再升：
1. 单机 RTO 承诺已无法满足业务（例如要求 ≤ 5s 无人值守切换）；
2. 记忆条数/写入速率导致单机整理窗口撞高峰（R13 判据长期不达标）；
3. 需要多副本读扩展；
4. 合规要求异地容灾（此时先做「A + ZFS send 异地」再谈 B）。
