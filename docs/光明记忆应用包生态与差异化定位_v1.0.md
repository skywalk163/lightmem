## 1. 向 NAS 学什么

### 1.1 参考事实（NAS 侧，均为公开可核）

| 观察对象 | 事实 | 对光明记忆的启示 |
|---|---|---|
| Synology 套件中心 | 套件 = 官方或第三方应用，可安装 / 运行 / 停止 / 卸载 / 更新；设置项含**信任等级、自动更新、社区套件来源、发行者证书** | 包必须有来源分级与信任等级，不能只有"能装" |
| TrueNAS SCALE 24.10 | Apps 后端从 Kubernetes 切到 Docker；自定义应用可用**引导向导**或 **Compose YAML**；官方 catalog 应用升级自动迁移，**第三方 catalog（如 TrueCharts）不自动迁移**；应用维护**独立于系统版本发布周期** | ① 包要与内核解耦 ② 第三方源必须显式标注"不保证迁移" ③ 包版本与内核版本各走各的 |
| TrueNAS 应用元数据 | 每个应用有 metadata：`train`（stable）、`version`、`icon`、`capabilities`、`portals`、`maintainers`、`sources` | 包的 manifest 要最小完备，能被 UI、CLI、AI 三种消费者读懂 |
| TrueNAS 升级与回滚 | 迁移时**保留旧 dataset**，因此可以回滚到上一版本 | 升级前打 ZFS 快照 = 天然回滚点（§5.6） |

### 1.2 提炼出的四条设计原则

1. **内核冻结，能力以包生长。** MemoryRouter / Storage / VoteFusion / 统一 Schema（§4.1）不因加包而改；新能力走包。
2. **包必须自描述。** manifest 是唯一真源，同时供人（UI）、机（CLI）、AI（编排）消费。
3. **包有完整生命周期。** 安装 → 配置 → 启用 → 健康检查 → 升级 → 禁用 → 卸载清理；每步有状态、有权限、有审计、可回滚。
4. **包来源分级 + 升级可回滚。** builtin（随内核）/ official（官方目录）/ community（社区）；升级前快照，迁移失败可退。

> **与 §2.6 可缩放模式的关系：** profile 决定"装哪些包"，包决定"档位能长多大"。Solo 档位不装 Redis/MQ/独立向量库；升到 SMB 时按 profile 声明补齐——**配置切换而非系统重写**的既有结论不变。

## 2. 包生态架构（LIMS App Package）

### 2.1 包的三层结构

```text
能力包（Scenario Bundle）        ← 交付单位，含多个包 + 配置 + 记忆模板
   └── 应用包（App Package）      ← 安装单位，一个可跑的服务/连接器/Skill 集
          └── 组件（Component）   ← 落地单位，jail / dataset / 端口 / 密钥
```

### 2.2 包的类型（v2.1）

| 类型 | 说明 | 举例 |
|---|---|---|
| `service` | 提供服务的独立程序（对应 NAS 的应用） | gitea、minio、qdrant、search |
| `connector` | 外部记忆连接器（§3.12） | git-connector、docs-connector、object-connector |
| `skill` | 面向 Agent 的能力（提示词 + 工具 + 记忆模板） | git-steward、doc-curator |
| `policy` | 写策略 / 脱敏 / 投毒防护规则（§3.15） | pii-mask、injection-guard |
| `pack` | 领域记忆包（可导入的初始记忆与词表） | 家庭实验室运维记忆包 |
| `scheduler` | 后台任务（备份、整合、巡检） | zfs-snapshot-job |

### 2.3 包清单文件（`manifest.yaml`，草案）

```yaml
id: gitea-connector
name: Gitea 记忆连接器
version: 0.1.0
kind: connector                # service|connector|skill|policy|pack|scheduler
api: lims/v1                   # 依赖的内核 API 版本
requires_core: ">=2.1,<3.0"    # 内核兼容区间（内核升级不强制包升级）
tier: family                   # solo|family|smb|enterprise 最低档位

requires:                      # 组件依赖（缺则拒绝安装或提示补齐）
  components: [gitea, postgresql]
  packages: []

landing:                       # 落地声明（FreeBSD + ZFS）
  jails: [lims-gitea]
  datasets:
    - { name: tank/lims/gitea, recordsize: 8k, compression: lz4 }
  ports: [3000, 2222]
  secrets: [gitea_admin_token] # 只声明引用，不入镜像/不入配置明文

permissions:                   # 扩展契约：能碰什么、不能碰什么
  memory_read: [repo_meta]     # 只读元数据
  memory_write: [repo_facts]   # 写入新记忆（追加）
  can_modify_core: false       # 禁止改内核
  network_egress: [git.internal]

lifecycle: [install, configure, enable, health, upgrade, disable, uninstall]
health:
  cmd: "gitea admin user list || exit 1"
  interval: 60s
audit: true
icon: https://.../gitea.svg
maintainers: ["tianma"]
sources: ["https://gitea.io"]
```

> 三条硬约束：① `can_modify_core` 恒为 `false`（内核只经内核版本升级）；② `secrets` 只声明 key，值由 §5.7 密钥管理注入；③ `tier` 低于当前 profile 的包**不展示**（避免 Solo 误装集合体组件）。

### 2.4 与既有章节的接线（不新增机制，只做映射）

| 包机制 | 复用既有能力 |
|---|---|
| 包落地 jail/dataset | §5.7 jail + §5.6 ZFS dataset 布局 |
| 包生成的记忆 | §4.1 统一 Schema（`memory_kind=fact/event`，不新开结构） |
| 包的写校验 | §3.15 WritePolicy 插件注册表 |
| 包的经验沉淀 | §3.13 后台整合（候选需人工确认）→ `procedure` |
| 包操作审计 | §7.2 AuditLogger（含包版本、操作人、前后值） |
| 包升级回滚 | §5.6 ZFS 快照 + `zfs send/receive` |
| 包需要的档位 | §2.6 `lims.profile.yaml` profile |

## 3. 必备功能包清单

### 3.1 第一批（P9 交付，与 §6「应用包」章节映射）

| 包 ID | 类型 | 是什么 | 为什么是"必备" |
|---|---|---|---|
| `gitea` | service | 自托管 Git 服务（仓库/Issue/PR/Wiki/Actions，单二进制） | **记忆的版本化底座**：技能、策略、记忆包都用 Git 管版本，可 diff、可回滚、可审计（对齐 Letta "memory as code" 方向） |
| `git-connector` | connector | 把 Git 仓库接入记忆：记提交摘要、Issue/PR 结论、Wiki 索引 | 代码协作里的一等事实（"为什么这么改"）不再丢失 |
| `registry` | service | 本地包/镜像注册中心（OCI + 包元数据） | 包生态自举：内网可拉包、可离线安装，不依赖外网 |
| `backup` | scheduler | ZFS 快照 + `zfs send/receive` 定时任务 | 唯一"可回滚"保障；升级前必跑（对齐 TrueNAS 保留旧 dataset 的回滚思路） |
| `search` | service | 全文本检索（BM25）+ 分词 | §3.4 多信号的关键词信号依赖它；缺则检索降级 |
| `llm-gateway` | service | 多后端模型网关（DeepSeek / Qwen / 本地） | 记忆抽取与整合的算力入口，token 计费与限流在此收口 |
| `mesh-sync` | service | 集合体互联（节点发现、授权声明交换、revocation 广播） | §5.5 集合体的最小实现 |
| `webui` | service | 管理后台：记忆浏览、retrieval_trace、包管理页 | §6.1 前端单元落地 |

### 3.2 第二批（按需启用，不进首日）

| 包 ID | 类型 | 触发条件 |
|---|---|---|
| `vector-qdrant` | service | 单租户向量行数 > 500 万 或 检索 P95 超红线 60%（§6 迁移阈值） |
| `tsdb` | service | 需要把时序指标（KPI 达成）作为一等记忆 |
| `msg-bus` | service | 需要跨节点事件（SMB+） |
| `object-store` | service | L3 冷归档量级超出本地 dataset 预算 |
| `bigdata` | service | Enterprise 档位的离线分析 |
| `backup-remote` | scheduler | 需要异地容灾 |
| `ai-lab` | service | 记忆抽取/融合的离线实验台（评测集跑批） |
| `pipeline` | service | 批量导入/导出与转换流水线 |

> 第二批全部**默认关闭**，由 profile + 触发条件决定是否展示（同 §2.3 的 `tier` 规则）。

### 3.3 包与记忆的接线原则

- 包安装**不改内核代码**；包通过 `manifest.permissions` 声明它可以读/写哪些 `memory_kind`。
- 包产生的记忆**一律走 §3.3 MemoryExtractor 的只增路径**，禁止包直接改历史记忆（只增语义不受包影响）。
- 包的配置变更、装/卸/升级**必须落 §7.2 审计**，并带 `trace_id`。
- 包自带的领域词表/别名表 → 交给 §3.14 EntityLinker；不得各自维护一套实体表。

## 4. AI 协同：光明记忆与常规 NAS 的真正分界

常规 NAS 的本质是**人类驱动的人工平台**：人看应用商店、人选应用、人填配置、人排错、人写文档，平台只负责装和跑。
光明记忆的本质是**AI 与人协同的记忆平台**：同样的包装进系统后，AI 会读它、配它、用它、并从使用中沉淀经验。

### 4.1 记忆主体的扩展（v2.1 关键概念）

> **包不只是程序，包是被记忆的一等实体。**

传统 NAS：应用是黑盒；人对应用的了解存在自己脑子里，换人即失传。
光明记忆：每个包在 §4.1 统一 Schema 下拥有自己的记忆集——

| 包记忆 | memory_kind | 说明 |
|---|---|---|
| 包是什么、能干什么 | `fact` | 从 manifest + 文档抽取，写入 L2 |
| 这台机器上它是怎么配的 | `fact`（带 `reference_frame.project`） | 配置决策与理由，形成本地知识 |
| 出过什么故障、怎么修的 | `event` → 后台整合 → `procedure` | **运维经验沉淀，这是 NAS 给不了的** |
| 它属于谁的授权范围 | `permission` 三元组 | 谁的可读/可写，与 §7.1 一致 |
| 它现在健康与否 | `event`（带 `occurred_at`） | 由 `scheduler` 包定时巡检写入 |

### 4.2 四个协同环节

**① 装包（AI 辅助选型与安装）**
人给意图（"我要在这台 FreeBSD 上做代码托管 + 变更留痕"），AI：读 profile（§2.6）判断档位 → 查包目录过滤 `tier` 不符项 → 生成 `gitea + git-connector + backup` 组合建议 → 按 §5.7 生成 jail/dataset/pf 具体命令 → **高风险动作（开机自启、外露端口、密钥写入）必须人工确认后才执行**。

**② 配包（配置记忆化 + 冲突检测）**
AI 把每次配置决策写成带理由的 `fact`（"为什么 gitea 用 SQLite 而不是 PG：Family 档位并发低"）。下次同配置出现时，AI 先查历史：若与既有 decision 冲突（如上次记录了"必须用 PG"），**触发 §3.4 冲突标记而非静默覆盖**。

**③ 用包（包作为记忆提供者）**
`git-connector` 把仓库的提交/评审结论转成记忆；`llm-gateway` 让抽取有算力；`search` 提供 BM25 信号。**包既是能力来源，也是记忆来源**——这是"记忆平台 + 应用包"与"应用平台 + 外挂记忆插件"的根本区别。

**④ 沉淀包经验（后台整合，闭环）**
§3.13 BackgroundConsolidation 离线扫描同 `reference_frame`（同机器、同包）的历史 `event`，提炼为 `procedure` 候选（如"FreeBSD 上 pkg 升级后必须重启 jail"），**经人工确认**后升为长期记忆，并向同用户名下其他 Agent 共享（`visibility=shared_user`，§3.2）。于是"这台机器的运维经验"从个人经验变成组织资产。

### 4.3 边界与不承诺

- AI 协同**不绕过权限**：包记忆同样受 §7.1 硬过滤与 `permission` 三元组约束；跨 Agent 共享仍走二次确认。
- AI 不得自动执行高风险动作：开机自启变更、对外端口暴露、删除、密钥操作——**一律人工确认**（与 §7.5 投毒防护的"共享前人工确认"同源）。
- AI 推荐的包组合**不替代专业判断**：安全合规场景下，AI 输出仅为信息性建议，最终实施由人负责。
- 包冲突（如两个包抢端口/改同一 dataset）必须显式报错，禁止 AI 自行"择一执行"。

## 5. 我们的特色：六条护城河

> 排序按"别人短期抄不走"的程度从高到低。第 1、2 条是主特色。

### 特色 1（主）：**低 token 长期运行——用光明语言把记忆系统的常驻成本压下来**

**这条是用户本次加入的，也是最有辨识度的。** 它的成立需要两个条件同时满足，而我们两个都有：

- **条件 A：记忆系统本身要省 token。** 光明记忆的架构天然省：线索优先（§2.4 只存摘要不搬全文）、核心记忆块常驻替代全量上下文（§3.7）、后台整合把 N 条 event 压成 1 条 procedure（§3.13）、双时态让"读时融合"取代"写入时对账"（§3.3，省掉一次 LLM 调用）。架构侧已对齐行业最优做法。
- **条件 B：系统自身的程序性部分要用"低 token 语言"表达。** 这正是**光明语言的加成**：持久化编码实践青睐表意密集写法——同一语义，用**汉字/文言体表达比 ASCII 英文更短**（信息密度高～1.5–2 倍），且 L0 仅 30 个冻结核心字即可组合出全部高层语法，语法面小、模型学习与生成成本低。

**写成一句可对外的话：**

> 光明记忆把记忆系统的**数据面**（记忆内容）和**控制面**（编排规则、策略、整合流程、包配置）都压缩表达；
> 数据面靠架构省 token，控制面靠光明语言的表意密度省 token。
> 结果：**维持整套记忆生态所需的 token，低于其它竞品。**

**为什么竞品难抄：** Mem0 / Zep / Letta 的控制面是 Python/TS 工程代码 + 自然语言提示词，其 token 成本模型里**没有"语言本身"这一维**。我们能调的不只是"检索返回几条"，而是"表达同一逻辑要多少 token"。这是语言层优势，不是功能层优势——功能可以抄袭，兑换率不能。

**待验证（诚实标注）：** "低 token 长期运行"目前是**设计主张**，需要在 §7 评测矩阵上给出与竞品的同口径对比数字（见 §8.3 的落数字方案）。在拿到数据前，对外表述应写"架构与语言双重优化"，不写"已验证优于 X%"。

### 特色 2（主）：**可长期运行、不烧钱——因为省 token 才能实现 AI 协同**

"AI 协同"这个词很便宜，人人都在说；但它有个前置条件：**AI 得一直在场**。而 AI 一直在场的成本 = token。凡是靠"每轮塞全量上下文 + 每轮调抽取 LLM"的方案，长期运行的账单会先崩——行业里已有明确信号：S&P Global 分析师指出 Zep 在企业规模下**运行成本昂贵**，并判断"成本敏感度上升会推动企业寻找更经济的方案"。LangMem 的 p50 检索延迟约 18 秒，也说明重编排路线在交互场景下的代价。

所以我们真正的表述是：

> **别人提供记忆，我们提供"跑得起的长期记忆"。**
> 低 token 不是为了省钱，而是为了让 AI 协同**在经济上可持续**——这是 §4 那四件事（装包/配包/用包/沉淀）能一直做下去的前提。

### 特色 3：**记忆即文件、记忆即 Git——可版本化、可回滚、可审计**

LIMS 的结构天然落在文件系统上（PG 元数据 + ZFS dataset + 对象归档），再加 gitea 包，就能把**技能、策略、包配置、记忆包**全部纳入 Git：可 diff、可 review、可回滚。Letta 的 Context Repositories 也指向同一方向，但我们是**从存储层（ZFS）到应用层（Git）打通**，且回滚是真的存储级回滚（快照 + `zfs send`），不只是版本号。

### 特色 4：**自托管 + 数据主权完整，且能在 FreeBSD 上"低功耗常驻"**

级联删除（§7.3）、一键导出（§7.4）、审计（§7.2）、投毒防护（§7.5）本就强于多数开源默认实现（Mem0/Letta/Zep 默认只提供 delete API）。叠加 FreeBSD + jail + ZFS 后，可以在**一台低功耗机器上长期常驻**：Gitea 空闲内存约 40–80MB（社区实测口径），Go 单元静态二进制，与"家庭实验室长期运行"的场景严丝合缝。竞品多为 Python + 多进程微服务，常驻成本与运维复杂度更高。

### 特色 5：**AI 可自主编排的应用包生态**

见 §4。常规 NAS 的应用商店是给人点的；LIMS 的包（§2.3）是**给 AI 读的**——manifest 声明依赖、权限、落地方式、成本（token 预算），AI 才能安全地组合、安装、排障、沉淀经验。

### 特色 6：**双时态 + 只增融合 + 多信号 rank 融合**

是对既有优势的确认而非新创：Zep 的双时态很强、Mem0 的多信号很强，但把**双时态 + 只增 + rank 融合 + 绝对分下限 + 多租户硬过滤 + trace 可解释**放在一套设计里，是 LIMS 的独有组合。特别是 `retrieval_trace`（§4.3）对"记忆污染排查"的支撑，在开源方案里少见。

## 6. 竞品对照

### 6.1 定位对照

| 维度 | 光明记忆 LIMS | Mem0 | Zep / Graphiti | Letta (MemGPT) | 常规 NAS（Synology / TrueNAS） |
|---|---|---|---|---|---|
| 定位 | 可长期运行的记忆平台 + 应用包生态 | 即插即用记忆库 | 企业时序知识图谱 | Agent 运行时 + 记忆 | 文件与应用托管平台 |

### 6.2 一句话定位（对外可用）

- 对竞品：**"Mem0 让 Agent 记住；WeZep/Zep 让 Agent 记住时间；光明记忆让 Agent 记得起、跑得久、还省得起。"**
- 对 NAS：**"NAS 是放应用的柜子；光明记忆是会用这些应用、并记住怎么用的记忆平台。"**

## 8. 落地增量与风险

### 8.1 路线图增量（P9）

| 阶段 | 周期 | 内容 |
|---|---|---|
| P9 应用包生态 | 4~6 周 | `manifest.yaml` schema 定稿；包生命周期 API（install/enable/configure/health/upgrade/disable/uninstall）；包目录 + 信任分级；首批包（gitea、git-connector、registry、backup、search、llm-gateway、webui 的包管理页）；包记忆抽取与审计接线；M2/M7 指标埋点 |

> P9 排在 P8（集合体与多后端）之后：包的单机形态不依赖集合体，但 registry / mesh-sync 的价值在 SMB+ 档位才显现。若家庭实验室要**尽快**用上，可把 `gitea` + `git-connector` + `backup` 三个包前置到 P8 并行做。

### 8.2 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 包破坏内核边界 | 高 | `can_modify_core=false` 硬约束；包只经公开 API；审计必写 |
| 包供应链攻击 | 高 | 信任分级 + 发布者证书（对齐 Synology 套件中心做法）+ 校验和；社区包默认不自动升级 |
| 包升级导致记忆 schema 漂移 | 高 | 包必须声明 `requires_core`；schema 变更只走内核版本，包跟随 |
| AI 协同误操作生产环境 | 高 | 高风险动作强制人工确认（§4.3）；包冲突显式报错 |
| 第三方源不保证迁移 | 中 | 显式标注（对齐 TrueNAS 对 TrueCharts 的处理）；升级前快照 |
| M2 指标做不出来 | 中 | 若控制面 token 优势无法量化，对外只主张"架构省 token"，撤回语言层主张——**先有数字再有说法** |

### 8.3 让"低 token"落成数字（三步）

1. **建基线：** 在 §8 P2.5 评测集上跑三个参照实现的同负载对比（全量上下文、Mem0 风格单遍只增、LIMS 架构）。
2. **分离度量：** 把 token 拆成"数据面（记忆内容）+ 控制面（编排/策略/配置）"，分别计量——**控制面差异才是光明语言的贡献**。
3. **公开口径：** 只公布可复现口径（说明查询集、模型、轮次、是否含 embedding 计费），并把评测脚本纳入仓库。

## 9. 结论

1. **向 NAS 学的是"内核冻结 + 包自描述 + 生命周期治理 + 来源分级 + 可回滚"**，不是学它的应用商店界面。
2. **必备包分两批：** 首批 8 个（gitea 为核心的协作与底座），第二批按触发条件启用，全部默认关闭。
3. **与常规 NAS 的分界是 AI 协同：** 装包、配包、用包、沉淀包经验四件事里，包本身成为**被记忆的一等实体**，运维经验自动提炼为 `procedure`。
4. **我们的特色是六条，前两条是主：** ① 低 token 长期运行（数据面架构 + 控制面光明语言双重压缩，是竞品**没有维度**可抄的优势）；② 正因省 token，"AI 协同"才在经济上可持续——别人给记忆，我们给跑得起的记忆。后四条目：记忆即 Git、自托管数据主权 + FreeBSD 低功耗常驻、AI 可编排的包生态、双时态 + 只增 + rank 融合的独有组合。
5. **诚实边界：** "低 token"目前是设计主张，须由 M2/M4 指标落数字后再对外主张；在此之前表述为"架构与语言双重优化"。
