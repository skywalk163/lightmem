## 5. 安全对比

### 5.1 fail-closed 启动护栏：只有 gitea 有（P0）

提交 `30ff8e4`（2026-11-02 00:51 +0000）「feat(auth): 启动期 fail-closed 护栏——非回环监听且
无 token 时拒绝启动」，`141 insertions, 0 deletions`，4 文件。

代码里的背景（`kernel/auth.go` 护栏段注释原文）：

> 两个默认值单独看都合理，叠在一起就是一个开放的记忆库——
> A. `-listen` 默认是 `:8080` / `:18444`，Go 里等价于 `0.0.0.0`，即监听所有网卡；
> B. 未配置 `LIMS_AGENT_TOKENS` 时 `AuthMiddleware` 直接放行。
> 于是「下载二进制 → 直接跑 → 忘了配 token」会得到一个监听全网卡、无任何认证、
> 可读写全部记忆的服务。记忆里是架构决策与客户背景，这个默认值不能留。

护栏形态：不改「默认透传」的既有语义（红线④），而是在 main 启动期加：

- `IsLoopbackAddr(addr)`：`:8080`、`0.0.0.0:8080`、`[::]:8080`、空串**一律判非回环**（宁可误拦）
- `AgentTokenCount()`：返回已装配 token 条数
- 非回环监听 + token 数为 0 → **拒绝启动**（`lightmem-kernel` 与 `lightmem-mcp` 两处）
- quickstart 不受影响（`install.sh` 默认 `BIND=127.0.0.1` 且签发 token）

**GitHub 侧核验结果：**

```
$ git grep -n 'fail-closed\|LoopbackGuard\|RequireTokenWhenNonLoopback' github/main -- kernel
（无输出）
$ git cat-file -e github/main:kernel/auth_loopback_guard_test.go
fatal: path 'kernel/auth_loopback_guard_test.go' exists on disk, but not in 'github/main'
```

→ GitHub main 上**没有**这道护栏，也**没有**它的测试。

## 9. 可选方案与推荐（**均未执行**）

> 前提：§4 已证明「右侧 tip 无独有代码」。以下代价都在这个前提下重新估算，
> 比卡片初稿里「84 vs 67，可能是两套并行工作」的假设**小一个数量级**。

### 方案甲：以 gitea 为准，把 GitHub 侧 67 个 cherry-pick 回来

- **实际结果：空转。** 64 个 patch 已等价，剩下 3 个（2 文档 + 1 sec）内容也已在树上。
  cherry-pick 只会产生 64 个重复补丁 + 3 个空提交。
- 代价：0.5–1 天（逐个处理冲突/空提交），换来的代码增量 = **0**。
- 结论：**不推荐**。原始假设「那 67 个是不是真需要」已有答案：**不需要，因为已经在了**。

### 方案乙：以 gitea 为准，强推覆盖 GitHub（force-push）

- **技术前提已满足**：树级无损（唯一「丢」的是 49 个内部文档 + 1 个 docx，都是主仓有意移除的，
  而且这 49 份正是 §5.4 的泄露源——覆盖它们**顺带**让它们从 main 消失）。
- 代价：**历史被改写，不可逆**；GitHub 上基于旧 main 的 fork / PR 全部错位；
  镜像侧 67 个 SHA 永久不可达（除非有本地备份）。
- ⚠️ **必须业主明确批准**；本卡不替你决定。
- 副作用（正面的）：护栏 12 天内上线，main 上不再有内网拓扑文档。
- 副作用（需要另处理）：**泄露文件仍在 GitHub 历史里**，force-push 清不掉。

### 方案丙：两边合流，做一次真 merge

- 冲突面其实很小（按 §4 只可能撞 `README.md` / `go.mod` / `.gitignore` / `.dumate`），
  冲突概率比卡片预估的「84 vs 67」低得多。
- 代价：半天到 1 天；结果是 151 个提交的合并图 + 一个 merge commit，
  `README.md` 需要手工取「左侧版本 + 右侧增补」，`.dumate/` 需要决定是否复活（**不要复活**）。
- 收益：GitHub 侧 67 个 SHA 保持可达；历史最"完整"但也最脏。
- 结论：可行但收益 < 成本。

### 方案丁（**推荐**）：以 gitea 为准，`merge -s ours` 做「声明式合流」，再普通 push

```
# 仅示意，本卡未执行、也不建议 agent 自行执行
git checkout main
git merge -s ours github/main -m "chore(sync): 以主仓为准合流 GitHub 镜像血线（内容取主仓，保留镜像历史可达）"
git push origin main
git push github main          # 普通推送，非 force
git push github v0.1.0        # tag 已在，可不推
```

- 效果：**不改写任何历史**；GitHub main 前进到「主仓树 + 1 个 merge commit」；
  镜像侧 67 个 SHA 仍然可达（审计/回溯不断），护栏随树上线。
- 代价：1 个 merge commit；GitHub main 的树内容与主仓一致（`.dumate/` 随之从 main 消失）。
- 前提：业主点头（涉及 push + merge，两条都在本卡红线内）。
- 风险：`-s ours` 是"我全要我的"，语义上等于「右侧历史保留、内容作废」，
  需要 commit message 写清楚，否则下一个人会看不懂为什么 merge 后内容全变了。

### 方案戊（安全兜底，与丁并行，另开卡）：清掉公开历史里的内网文档

- 选项：① 把 GitHub 仓库改成 private；② 重建仓库（新 repo 只推主仓历史）；
  ③ 用 `git filter-repo` 重写历史后 force-push（破坏性最大，仍需业主批准）。
- 这只是 §5.4 的处置，与分叉合流**解耦**：即使不做丁，也应该做它。

### 方案对比与推荐

| 方案 | 代码增量 | 护栏上线 | 历史 | 工作量 | 破坏性 | 推荐 |
|---|---|---|---|---|---|---|
| 甲 cherry-pick | 0 | 需再推 | 整洁 | 0.5–1 天 | 无 | ❌ 空转 |
| 乙 force-push | 0 | ✅ | **改写** | 10 分钟 | **高、不可逆** | 需业主批准 |
| 丙 真 merge | 0 | ✅ | 更脏 | 0.5–1 天 | 低 | ⚠️ 次选 |
| **丁 `-s ours`** | 0 | ✅ | **不改写** | **10 分钟** | 低 | ✅ **推荐** |
| 戊 清历史 | — | — | 取决于选项 | 0.5 天–1 天 | 中-高 | ✅ 并行另卡 |

**推荐：丁 + 戊（另卡）。** 理由：

1. 既然右侧无独有代码，**任何"把右侧内容搬回来"的动作都是零收益**——只剩「怎么让镜像追上」
   的问题，而 `-s ours` 是唯一「不丢历史、不改写、10 分钟完事」的形态。
2. 护栏是**已上线的代码**，不是待开发的特性；镜像落后一天，README 就在多误导一天人。
3. §5.4 的泄露与合流是两件事，混在一张卡里做会让"是否 force"变成安全压力下的仓促决定。
