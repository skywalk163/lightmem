## §0 结论摘要

**1. 目标要拆成两层，不能混为一谈。**
「进程的可持续性」与「记忆的耐久性」是两个独立失效域：进程死了靠守护拉起（秒级），记忆丢了只能靠 WAL/快照（分钟级）。混在一起谈，必然做出「重启了但失忆」的假高可用。

**2. 骨架比想象中完整，断线集中在四处「声明 ≠ 接线」。**
`/healthz` 已带存储探针（`server_metrics.go:300` `HealthzHandler`）、整合 worker 已有 5 分钟 ticker（`consolidate.go:48-50` `NewConsolidator`）、访问计数已有落库定时器（`main.go:172-189`）、FreeBSD rc.d 已有 PG 就绪等待与启动后健康等待（`lims-088-rc.d/lightmem:118,213-222`）、ZFS 快照+send 已是可复跑脚本（`scripts/zfs_backup.sh`）。

**3. 生产机（FreeBSD 0.88）今天不具备崩溃自愈；但补上不是改一行那么简单。**
rc.d 用 `daemon -f -u -P -o` 起进程（`lims-088-rc.d/lightmem:197,205`），**无 `-r`/`-R`** → 进程一崩即永久宕机。
**v1.1 修订**：加 `-r` 会同时引入两个新风险——① 启动期 fail-fast（PG 缺表/配置错/端口占用）变成崩溃循环；② 现有 stop 顺序（**先 `pkill` 子进程、再 kill supervisor**，`lightmem:133,136`）在 `-r` 下存在竞态（杀掉子进程后 supervisor 立即拉起新的，再杀 supervisor 可能留下新子进程）。
→ 本版给出**原生防抖方案**：较新的 `daemon(8)` 已提供 `-R`（重启延迟）与 `-C`（**重启次数上限**，最大 128），配合 stop 顺序修正 + 外部 watchdog 兜底。**先 watchdog（零侵入），验证稳定后再启用 `-R/-C`。**

**4. 最危险的一条不在崩溃，而在「重启成功但连错了库」。**
`PGConfig.Primary / Replica / Sharding` 在 `profile.go:87-89` 有定义，**全仓零调用点**；`newPgBackend` 只读 `cfg.PG.Host`（`backend_pg.go:42-56`），而 `lims-smb.profile.yaml:21-31` 与 `lims-enterprise.profile.yaml:15-32` **都没有设 `pg.host`**。同时 `docs/档位能力矩阵.md:15,29` 对外声明 SMB 为「单节点/双节点主备」「单库/主备」。
→ **v1.1 决定默认走「如实降级」**：补 `pg.host` + `validate()` 启动期 fail-fast + 文档明确标注「主备未接线」。**自动故障转移明确出范围**（需 fencing/防脑裂/VIP/DNS/提升备库，另立项目）。

**5. 落地顺序**：P0-A 守护（**零代码**，仅部署配置）→ P0-B 守护强化（改 rc.d 脚本，需真机复核）→ P1 健康三端点拆分 + 停机排水 → P2 睡眠调度器 → P3 耐久显式化 + 恢复自检 + 主备如实降级。

> **口径修正（评审第 1 点）**：**P0 = 不含 Go 业务代码改动，但含部署配置 / 脚本 / profile / 文档改动。** 且**严重度 ≠ 阶段**——见 §2.2 与实际路线 §5。

| 层 | 目标命题 | 现状 | 缺口 |
|---|---|---|---|
| L1 进程守护 | 崩溃后自动恢复，人工介入从「必须」降为「可选」 | Linux 有 systemd 单元（`Restart=on-failure`）；FreeBSD 无自重启 | G1 G2 G13 G16 |
| L2 健康语义 | 「活着」「可用」「能读记忆」三者可区分 | 有 Ping 探针；**无 liveness/readiness 分离**，PG 缺表仍 200 | G3 G4 G11 |
| L3 睡眠整理 | 低峰整理不阻塞在线，停机不留半成品 | 整合有调度但无窗口/预算/排水；5 引擎无调度 | G5 G6 G7 G8 G9 |
| L4 持久与恢复 | 重启后时间线可接续，RPO/RTO 可承诺 | WAL 开关已有；同步级别/checkpoint/恢复自检缺；主备未接线 | G10 G11 G12 G14 |

## §1 目标、口径与非目标

### 1.1 把「永续」拆成四个可证伪命题

| 命题 | 可证伪的判据（不满足即不成立） |
|---|---|
| **C1 进程可持续** | `kill -9 $(pgrep -f lightmem-kernel)` 后无需人工介入，服务在 T 秒内监听同一端口，且鉴权矩阵复验通过 |
| **C2 可用性可判定** | 记忆不可读时，**守护层拿到的探针是失败**（而不是「进程在、接口全 500」） |
| **C3 记忆可维护** | 整理窗口内在线读写 P95 劣化 ≤ 20%（方法见 §7.1），且窗口被中断不留不一致状态 |
| **C4 时间线可接续** | 崩溃/断电重启后**已确认写入**条数一致，且日志明确记录从哪个状态恢复 |

### 1.2 大脑隐喻 → 工程状态机

| 大脑态 | 工程态 | 触发 | 对外可用性 | 失败回退 |
|---|---|---|---|---|
| 清醒 | **Serving** | 常驻 | 读写全可用 | → 昏迷（崩溃）/ 小睡（窗口到） |
| 小睡 | **Maintenance** | 低峰窗口 / 固定间隔 | **目标态**：读写照常；**现状（Solo 档）**：可用但可能延迟尖刺（G8） | 整理失败退避，不影响 Serving |
| 深睡 | **Snapshot** | ZFS 定时快照 / `zfs send` | 读写照常；快照近零成本，`send` 需限速 | 快照失败告警，下轮重试 |
| 打盹 | **Supervised** | 进程不在但守护者在 | 不可用（秒级） | 守护拉起 → Serving |
| 昏迷→苏醒 | **Recovery** | 进程意外退出 / 主机重启 | 不可用（T 秒级） | 自检 → 声明 ready → Serving |

> ⚠️ Maintenance 行区分「目标态 / 现状」是评审第 11 点要求：**v1.0 把目标态当现状写**，会让读者误判 Solo 档今天的整理代价。

**不变式（v1.1 重写为可证伪，评审第 12 点）**：

- **I1**：Serving / Maintenance / Snapshot 三态下，API 层**不得因自身逻辑**返回 5xx。
  - 判定口径：**依赖不可用**（PG/SQLite 打不开）导致的 503 **不算**「主动 5xx」——它由 L2 探针负责对外表达；
  - 维护导致的写排队**必须**返回 `429`（首选）或 `503` + `Retry-After`，并计入 `write_queue_depth` / `write_rejected_total`；
  - 「静默降级」（无日志、无指标）视为缺陷。
- **I2**：任何状态迁移必须落日志 + 计数指标（指标集见 §3.2.5）。
- **I3**：Recovery 态在完成恢复自检前**不得声明 ready**。

### 1.3 非目标（明确不做）

- 不做跨机房双活 / 异地多活（本设计只到**主备声明**与**可恢复**）。
- **不做 PG 自动故障转移**（评审第 6 点）：自动切换需要 fencing、防脑裂、VIP/DNS 漂移、备库提升与回退策略，属独立项目；本设计只做「主备声明 + 人工提升 + 启动校验」。
- 不引入 Kubernetes Operator、不做自动扩缩容。
- **不加任何第三方依赖**（调度器用 stdlib）。
- 不改 `model.go` / `storage.go` / `lifecycle.go` / `compliance.go` 的 Schema 语义，不动 `kernel/migrations/*.sql`。
- 不做应用内 fork 自拉起（反模式 §3.1.5）。

## §3 四层架构设计

### 3.1 L1 进程守护（Supervision）

#### 3.1.1 三层守护模型

```
第 1 层 init（rc.d / systemd）        —— 开机起、关机停 + 依赖顺序（等 PG）
第 2 层 supervisor（daemon -R -C / systemd Restart）—— 崩了拉起来 + 防抖
第 3 层 应用内自愈（Go 进程内）        —— 不自杀：降级服务而不是 exit
```

- 第 3 层**绝不**主动 `os.Exit`（除启动期 fail-fast 与 §3.3.4 的排水硬兜底）。
- 第 2 层只负责拉起与节流，不做业务判断。
- 第 1 层只管顺序与生命周期。

#### 3.1.2 FreeBSD：`-R / -C` 原生防抖（评审第 2 点的正面解法）

**先说结论**：现代 `daemon(8)` **不只有 `-r`**。按 FreeBSD 15.1 手册（[daemon(8)](https://man.freebsd.org/cgi/man.cgi?query=daemon&sektion=8&format=ascii)）：

| 选项 | 语义 | 用途 |
|---|---|---|
| `-r` | 监督并在**固定 1 秒**延迟后重启 | 最简自愈（旧版本即有此语义） |
| `-R seconds` | 监督并在**指定延迟**后重启（1–31536000） | **节流**：把崩溃风暴压成「每 N 秒最多一次」 |
| `-C count` | **最多重启 count 次**（上限 128；用尽后 `daemon` 自身退出） | **防抖上限**：不可自愈故障不再无限刷 |
| `-H` | 收到 SIGHUP 时重开 `-o` 日志文件 | 配合 `newsyslog` 做**日志轮转**（关 G16） |

**⚠️ 必须先在本机确认支持范围（R23）**：
```sh
man daemon | grep -e -- '--restart' -e -- '--restart-count' -e -- '--sighup'
daemon 2>&1 | head -5     # 或无参运行看 usage
```
较老的 FreeBSD 只有 `-r`。**不支持 `-R/-C` 时走 §3.1.3 的 wrapper 节流兜底**，不要裸上 `-r`。

**推荐参数（0.88，验证支持后）**：
```sh
/usr/sbin/daemon -f -H -R 5 -C 24 -u "${lightmem_user}" -P "${pidfile}" -o "${lightmem_log}" …
```
含义：崩溃后 5s 重启；**最多 24 次**（≈2 分钟内 24 次尝试，之后 `daemon` 退出，服务真正下线）→ 这正是想要的语义：**能自愈的自动好，不能自愈的停下来喊人**。

#### 3.1.3 两阶段落地（评审第 2 点：不要一步上 `-r`）

**阶段 P0-A（零侵入，先做）——cron watchdog + 冷却**
```sh
# /etc/cron.d/lightmem-watchdog
*/2 * * * * root fetch -q -T 5 -o /dev/null http://127.0.0.1:18443/readyz || \
  ( [ -f /var/run/lightmem/watchdog.cooldown ] || \
    ( touch /var/run/lightmem/watchdog.cooldown; \
      service lightmem restart; \
      logger -t lightmem-watchdog "restart triggered (readyz failed)"; \
      sleep 120; rm -f /var/run/lightmem/watchdog.cooldown ) )
```
- 冷却文件**必需**（否则 restart 期间探针必失败 → 每 2 分钟一次抖动被放大）；
- 探 `/readyz`（而非 `/healthz`），这样「进程在但记忆读不出」也会被处理——与 L2 联动；
- 不依赖任何 `daemon(8)` 新选项，**今天就能上**。

**阶段 P0-B（验证稳定后）——`daemon -R -C` + stop 顺序修正**
1. **stop 顺序必须改（评审第 2 点，v1.0 的「天然兼容」结论错误）**：
   手册明确：SIGTERM 发给**监督者**时，它会把信号转发给子进程，子进程退出、pidfile 移除、监督者随后终止。因此正确顺序是：
   ```
   ① kill -TERM "$(cat ${pidfile})"     # 先 supervisor：它会停子进程并自行退出
   ② 等待 supervisor 与子进程都消失（轮询，带超时）
   ③ pkill -f "${lightmem_pkill_pattern}"   # 兜底：清理孤儿（而非首选）
   ④ rm -f "${pidfile}"
   ```
   现有顺序（`lightmem:133` 先 `pkill` → `:136` 再 TERM）在 `-r/-R` 下会产生竞态：`pkill` 后监督者**立刻**拉起新子进程，随后 TERM 才到 → 可能留下新子进程占用端口 → 下次 start 报 `EADDRINUSE`。
   ⚠️ 该结论来自手册语义推演，**必须在 0.88 真机按 R1/R3 复验**。
2. **`-C` 用尽后的状态要有人管**：`daemon` 退出 = 服务真下线 → 保留 §3.1.3 的 watchdog 作为**最后一道兜底**（它会重新 `service start`，重置计数）+ 告警。
3. 加 `-H` + newsyslog（关 G16），避免长期运行撑满盘。

#### 3.1.4 wrapper 节流（仅当本机 `daemon(8)` 不支持 `-R/-C`）

用一个薄壳做「启动前冷却」，把无限重启压成有界：
```sh
#!/bin/sh
# /usr/local/lightmem/run-throttled.sh —— 供 daemon -r 调用
STATE=/var/run/lightmem/restart.state
now=$(date +%s); last=$(cat "$STATE" 2>/dev/null || echo 0)
if [ $((now - last)) -lt 5 ]; then sleep 5; fi      # 最小间隔
echo "$now" > "$STATE"
exec /usr/local/lightmem/lightmem-kernel -profile "$1" -listen "$2" -embedder "$3"
```
> 缺点：只是节流、**不是次数上限**；因此仍需 watchdog 告警。优先用原生 `-R/-C`。

#### 3.1.5 Linux / 容器（评审第 3 点：liveness 不能用含 Ping 的端点）

| 环境 | 配置 | 要点 |
|---|---|---|
| systemd | `Restart=always`、`RestartSec=2`、`StartLimitIntervalSec=60`/`StartLimitBurst=5`、`TimeoutStopSec=30`（≥ `-shutdown-timeout`）、`WorkingDirectory=/opt/lightmem` | `StartLimit*` 是「暂停自动重启」的**真正控制面**（见 §3.2.5） |
| 容器 | `livenessProbe` → **`/livez`**；`readinessProbe` → **`/readyz`**；`restart: always` | **绝不可**把含 `backend.Ping` 的 `/healthz` 当 liveness：PG 故障 → 探针失败 → 容器被重启 → **而重启治不了 PG**，会变成重启风暴 |
| 多服务 | MCP 独立单元/容器，`REQUIRES` 内核 | MCP 是下游（`lims-088-rc.d/README.md:12-13`） |

#### 3.1.6 反模式

- ❌ 应用内 `fork` 自身守护。
- ❌ 无节流/无上限重启（`-C`、`StartLimit*`、watchdog 冷却三选一以上）。
- ❌ 用「进程是否存在」（`pgrep`）或含依赖探测的 `/healthz` 当 liveness。
- ❌ 在 `-r` 语义下「先杀子进程再杀监督者」。

### 3.2 L2 分层健康（评审第 3、7、8 点）

#### 3.2.1 三个端点，三种语义

|---|---|---|---|---|
| **`/livez`（新增）** | 进程/HTTP server 活着 | 立即 200，**不碰任何依赖** | `livenessProbe`、守护脚本 | ❌ 缺失（v1.0 曾误把 `/healthz` 当 liveness） |

#### 3.2.2 `/readyz` 判据（含 TTL 缓存，评审第 7 点）

1. `backend.Ping(ctx)`；
2. **轻量读探针**：`SELECT 1 FROM memories LIMIT 1`（空表合法 → 200）；
3. **TTL 缓存 1–2s**：HTTP 请求只读缓存，实际探测由后台 goroutine 周期执行。

5. 响应**最小化**：`{"status":"ok|degraded","check":"..."}`——**不输出 profile / version / DSN / 后端名**（防信息泄露）；
6. 失败 → **503**。
7. `/livez`、`/readyz` 必须加入 `auth.go:264` 的运维端点豁免（否则探针 401 → 服务永远起不来，T3 已踩过；同步扩 `auth_test.go:692,713` 用例）。

#### 3.2.5 指标集与「暂停重启」的控制面（评审第 8、12 点）

**应用只暴露指标，不承担「暂停重启」**——它在进程内无法控制 supervisor。控制面归属：

| 能力 | 实现者 |
|---|---|
| 暂停自动重启 | systemd `StartLimit*` / watchdog 冷却文件 / **外部监控** |
| 重启计数 | supervisor（systemd 有 `NRestarts`）或外部 state 文件；**应用内计数不作为来源** |

| 指标 | 类型 | 含义 |
|---|---|---|
| `state_transitions_total{from,to,reason}` | counter | 状态机迁移（I2 的可证条件） |
| `maintenance_runs_total{job,result}` | counter | 每类后台任务的成功/失败 |
| `maintenance_skipped_total{job,reason}` | counter | 单飞跳过 / 预算用尽 |
| `drain_timeouts_total` | counter | 排水超时（含硬兜底触发） |
| `readyz_failures_total{check}` | counter | 就绪失败分类 |
| `backend_probe_ms` | histogram | 探针耗时（验证 TTL 缓存是否真的减负） |
| `write_queue_depth` / `write_rejected_total` | gauge / counter | I1 的写排队降级口径（429/503 + `Retry-After`） |

**告警阈值（评审文字意见）**：`last_consolidate` 停滞**不能**用固定 `3×interval`——窗口模式下白天停滞是正常的。判据改为：
```
now > 上次应运行时刻(window_next_run) + 2×Σ间隔  → 告警
```
即「按上次**应**运行时间算」，窗口模式下先算出窗口内的下一个应跑时刻。

### 3.3 L3 睡眠整理

#### 3.3.1 现状再陈述

- **整合**：已有 ticker（`consolidate.go:264`），默认 5min（`:49`），`main.go:145` 可覆盖。
- **生命周期 5 引擎**：有入口（`access.go:407`），**无调度器**（`main.go:195` 只注册路由）→ G7。
- **访问计数落库**：独立定时器（`main.go:172-189`），未设 env 时**不创建 goroutine**（`:172` 的 if 守卫）→ R12 零回归成立。

→ L3 不是「把 worker cron 起来」（已有），而是：**统一调度器 + 窗口/预算/退避 + 停机排水**。

#### 3.3.2 调度器设计（stdlib only，新增 `kernel/scheduler.go`）

```go
// 概念签名（示意，非最终实现）
type MaintenanceJob struct {
    Name     string                                   // "consolidate" | "lifecycle" | "access-flush"
    Interval time.Duration
    Window   *Window                                  // nil = 全时段（默认，零回归）
    Budget   Budget                                   // {MaxItems, MaxDuration, MaxWrites}
    Backoff  Backoff                                  // 1m → 2m → 4m … 封顶 30m
    Run      func(ctx context.Context) (Report, error)
}
```
四条硬规则：**单飞**（上一轮未完则跳过并计数）、**预算**（超限优雅让位，幂等所以下轮可续）、**退避**（连续失败指数退避 + 告警而非重启）、**窗口**（窗口外不启动新轮；窗口结束让当前轮跑完）。

#### 3.3.3 Solo 档「整理不阻塞」——不改既有接口语义（评审第 5 点）

v1.0 建议「把 `ScanAll` 改成分页」是**错的**：`ScanAll` 是 `MemoryScanner` 的全量语义（`consolidate.go:20-23`，唯一的消费点是 `RunOnce` `:66-74`），改它会破坏接口契约。**v1.1 改为新增**：

```go
// 新增（只增不改）：批量游标扫描，保持 ScanAll 原语义不动
type BatchedMemoryScanner interface {
    // ScanAllBatched 按 memory_id 游标（keyset）分批返回；after="" 表示从头
    ScanAllBatched(ctx context.Context, max int, after string, fn func(batch []*Memory) error) (next string, err error)
}
```
- **keyset（按 `memory_id` 游标）**，**不用 `OFFSET`**（并发写会漏/重）；
- **每批之间释放 `mu` 再让位**（否则「让出锁」不成立）：SQLite 侧实现为「每批一次 `loadAll` 级的受锁读取 → 出锁 → 回调处理 → `runtime.Gosched()`/`time.Sleep(1-5ms)`」；
- `sqliteBackend`/`pgBackend` 各加一个实现（`backend_sqlite.go:739` `ScanAll`、`backend_pg.go:628` `ScanAll` 保持不动）；
- **默认关**（`LIMS_MAINT_BATCH` 未设 = 走旧全表路径）→ **此时 G8 仍未关闭**，R13 必须写明开关（评审第 5 点）。
- 不采用「读/写锁分离」：SQLite 单连接下写仍阻塞读，收益有限而触碰既有并发模型，风险高。

#### 3.3.4 停机排水协议（评审第 4 点：两阶段 + 硬兜底）

```
① server.Shutdown(ctx)              停止接收新请求，等在途请求（已有 main.go:287-291）
② scheduler.Stop()                  不再启动新轮
③ cancel(bgCtx) + wg.Wait(soft)     等整合/生命周期/落库 goroutine 返回
   ├─ 正常返回 → ④
   └─ 超时     → 记录 drain_timeouts_total + 未完成标记（已原子写盘）→
                 **硬兜底：os.Exit(1)**（由 supervisor 拉起；启动自检会看到标记）
④ checkpoint（若启用）→ 清理未完成标记 → backend.Close()（main.go:300）
```

**关键修正**：**绝不允许**「超时后先 `backend.Close()` 仍让 goroutine 跑」——Go 无法杀 goroutine，后台任务会撞上 `sql: database is closed`，甚至 panic（评审第 4 点）。
**未完成标记落盘位置**：**数据目录**（与记忆同卷，不是 `/tmp`），原子写（`写 tmp → rename`），正常关闭时清理，启动时由 §3.4.4 读取。
> 取舍说明：硬兜底会让「一次不干净的关闭」变成一次重启，但**换来的是不死锁、不 panic、且状态可自证**。Q8 待确认可接受性。

#### 3.3.5 引擎接线矩阵（默认全关）

| 任务 | 现状触发 | 目标触发 | 默认 | **默认关时是否有 goroutine**（R12 可证条件） | 开关 |

#### 3.4.1 SQLite：把隐式默认变成显式契约（评审文字意见已纳入）

**先量基线再改**（评审第 15 点：只读打开，避免对生产库产生副作用）：
```sh
python3 -c "import sqlite3;c=sqlite3.connect('file:/usr/local/lightmem/data/lims.sqlite?mode=ro',uri=True);\
print('journal_mode=',c.execute('pragma journal_mode').fetchone()[0]);\
print('synchronous=',c.execute('pragma synchronous').fetchone()[0]);\

```
> `mode=ro` 保证不建 WAL、不加写锁。输出记入部署记录（R22）。

#### 3.4.2 路径与日志纪律

- `profiles/lims-solo.profile.yaml:21` 用**相对路径** `./data/lims.sqlite`（`:31` 归档同理）→ 谁启动进程决定数据落在哪。rc.d 用 `lightmem_chdir`（`lightmem:45`）钉住 ✅；quickstart 用绝对路径（`install.sh:77,141`）✅；`install.sh:329-331` 的 systemd 单元**无 `WorkingDirectory=`**（其自身 profile 是绝对路径，故今天无碍，但改指向时会踩）。
- **设计决定**：① 所有 supervisor 配置显式写绝对 chdir/WorkingDirectory；② 启动日志打印**解析后的绝对数据路径**；③ **绝不打印含口令的 DSN**（评审文字意见）——PG 口令应走 `secrets`/env（参见 HEAD `828229e` 的 R28 收紧）。

#### 3.4.4 启动恢复自检（评审第 13 点：查关键列/版本，不只 `SELECT 1`）

启动序列在「装配后端之后、声明 ready 之前」执行，输出**结构化一行日志** + 供 `/healthz` 读取：

| 检查 | SQLite | PG | 失败处置 |
|---|---|---|---|
| 可达 | `Ping`（`backend_sqlite.go:124`） | `Ping`（`backend_pg.go:89`） | fail-fast（已有：`main.go:78-81`） |
| **表存在** | 自建（`backend_sqlite.go:92`）→ 恒过 | `SELECT to_regclass('memories')` | **fail-fast** |
| **关键列存在** | `PRAGMA table_info(memories)` 断言 `memory_id, data` | `information_schema.columns` 断言 `memory_id, tenant_id, user_id, fact, recorded_at, superseded_by, vector_status`（真源 `migrations/001_pgvector.up.sql`） | **fail-fast**（缺列 = 迁移不匹配，别带病上线） |

| 恢复点 | WAL 大小 + `PRAGMA wal_checkpoint(PASSIVE)` | 备库时 `pg_last_xact_replay_timestamp()` | 记录 |
| 二进制 vs 库 | `VERSION`（`install_lims_rc_d.sh:129-134`） | 同 | 不一致 → 警告 + 继续 |
| 上次是否异常关闭 | 未完成标记（§3.3.4） | 同 | 记录；下轮整理自然收敛（A13） |

> 为什么不能只 `SELECT 1 FROM memories LIMIT 1`：它只证明**表名存在**，证明不了列与迁移版本匹配（评审第 13 点）。

**日志目标形态**：
```

       last_consolidate=2026-10-19T02:10:11Z unfinished_round=none
```

## §4 部署拓扑

### 4.1 拓扑 A —— 单机自愈（Solo / 轻 Family）

```
   rc.d: lightmem_enable=YES
     └─ daemon -f -H -R 5 -C 24 -P …（节流 + 次数上限）★G1/G16
          └─ lightmem-kernel :18443
               ├─ /livez（进程）  /healthz（综合）  /readyz（就绪）★G3
               ├─ 后台调度器（窗口+预算+排水）★G7/G5
               └─ 存储：SQLite WAL(sync=full)★G10 → ZFS zroot/lims
   cron watchdog（探 /readyz，带冷却）—— `-C` 用尽后的最后兜底
   cron + zfs_backup.sh send → 容灾池
```
承诺：RTO ≤ 5s（`-R/-C` 生效后）/ ≤ 2min（仅 watchdog）；RPO = 0（WAL）/ ≤ 1h（快照）。

### 4.2 拓扑 B —— 主备分离（SMB / Enterprise，目标态）

```
Agents ─► LB（readiness=/readyz）─► Gateway(无状态 ×N) ─► Coordinator
                                      │                     │
                                      └─► Worker ×N ────────┘
                                             │
                       PG 主（写）◄──────────┘
                         │ streaming（**声明态；提升＝人工**）
                       PG 备（只读/待提升）
                                             Maintenance Worker（独立进程）★G8
```
- 词汇表对应 `node_role.go:23-32`；一致性口径 `lightmem.md:1143-1161`。
- 角色当前为**骨架**（内存注册/广播，默认关；跨节点融合由 `features.cross_node_rank_merge` 控制）→ 拓扑 B 需先完成 G12 与角色接线。
- **自动故障转移不在本设计**（§1.3）。

### 4.3 何时从 A 升 B

满足**任意两条**再升：① 单机 RTO 承诺不满足；② R13 长期不达标；③ 需要多副本读扩展；④ 合规要求异地。
**合规前置（评审文字意见）**：先做「拓扑 A + `zfs send` 异地」，再谈 B。

### 7.1 R13 压测模板（评审第 10 点：可复现）

**固定条件（写进结果记录）**：数据集规模 N 条、并发 C、读写比、时长、**是否开 `LIMS_MAINT_BATCH`**、是否处于窗口内、重复 3 次取中位。

```sh
# 0) 造数据（示例：2000 条）；然后记下基线
# 1) 窗口外基线（同一并发）
python3 perf_probe.py --url http://127.0.0.1:18443 --token "$TOK" --tenant t1 \
        --seconds 60 --concurrency 8 --p95-out /tmp/p95_off.txt
# 2) 立即触发一轮整理，同时跑同样的负载
curl -s -X POST "http://127.0.0.1:18443/admin/lifecycle/run?engines=budget,archive&tenant_id=t1" -H "Authorization: Bearer $TOK"
python3 perf_probe.py --url … --p95-out /tmp/p95_on.txt
# 3) 比 p95 + 统计锁错误
python3 - <<'EOF'
a=float(open('/tmp/p95_off.txt').read()); b=float(open('/tmp/p95_on.txt').read())
print(f"off={a:.1f}ms on={b:.1f}ms 劣化={100*(b-a)/a:.1f}%  (判据 ≤20%)")
EOF
grep -c -e 'database is locked' -e 'database table is locked' /var/log/lightmem.log   # 期望 0
```
`perf_probe.py`（**待写，约 20 行，仅 stdlib**）：`threading` 起 C 个 worker 循环发 `GET /search?q=…` 或 `POST /tools/memory/recall`，记录每次耗时，输出 p50/p95/p99 到 `--p95-out`。
> 诚实标注：**未开 `LIMS_MAINT_BATCH` 时 G8 仍存在**，R13 只能在开启后声明通过。
