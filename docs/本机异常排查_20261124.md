## 0. 一句话结论

**"git 老卡着"不是 git 慢，而是四类独立缺陷叠在一条时间线上。** 同步状态机把 `rc=0` 一律当"刚快进"、git 子进程按 cp936 解码并继承管道、心跳每次新建线程池、看板只按 pid 号码判活——这四个问题各自都能让系统看起来"卡住"，合在一起就表现为"启动时 git 一直转、看板假活、日志刷屏、偶发进程消失"。

另外三件事与 hive 无关：DuMate 的 `0x10000002` 错误页是内嵌 `Dumate-agt` 被外部终止后的统一错误页；`light-merge` 的 ahead 是**提交没推**；`lightprism` 的 diverged 是**工作副本停在任务分支**。

| # | 现象 | 真实性质 | 严重度 |
|---|---|---|---|
| P1 | 启动后 git 长时间有进程、日志反复 `fast-forwarded 2914b4d… target=cde8a92…` | 状态机误判 + 补偿循环不收敛 | 高（持续空转） |
| P2 | `Exception in thread ... _readerthread: UnicodeDecodeError: 'gbk'` | git 输出 UTF-8 / 本地 cp936 解码 | 中（调用直接异常） |
| P3 | `维护循环异常：MemoryError()` ×31、`can't start new thread` ×3 | 心跳每轮新建 ThreadPoolExecutor | 高（hived 猝死、pid 被复用） |
| P4 | 看板 URL 打不开，但 `hive dash start` 说"已在运行" | `dashboard.pid` 号码被 conhost 复用 | 高（看板永远起不来） |
| P5 | DuMate 窗口变成"软件进程出现错误（0x10000002）" | `Dumate-agt` 被外部终止（exit 0），UI 统一错误页 | 中（单次，非崩溃） |
| P6 | `light-merge` 本地领先 `origin/main` 35、`gitea/main` 19 | 纯粹没推送 | 中 |
| P7 | `lightprism` 被判 `diverged` | 工作副本停在 `task/T-0337`，不是内容分叉 | 低（误报） |

## 2. 取证与根因

### P1 同步状态机：`rc=0` 不等于"刚快进"

**证据链：**

```
$ git -C light-merge rev-list --left-right --count HEAD...origin/main
35  0                                  # 本地领先 35，远端 0
$ git -C light-merge merge --ff-only origin/main
Already up to date.                    # rc=0，HEAD 没动
```

`hive.py:_sync_one_repo` 旧逻辑：

```python
if rc == 0:
    return {"repo": name, ..., "status": "fast-forwarded",
            "sha": rev_parse(path, "HEAD") or remote}
```

本地领先时 git 只回 "Already up to date."，于是记录变成 `status=fast-forwarded` + `sha=本地HEAD` + `target=远端SHA`。`RepoSyncAgent._reconcile` 每 300 秒比对 `cur["sha"] == target`，永远不相等 → 再同步 → 再记录，**永不收敛**。

`cluster.log` 里同一对 SHA 出现 **99 次**，间隔 4–5 分钟：

```
[hive-cluster 08:09:42] sync: light fast-forwarded 2914b4d612a3 target=cde8a92a3594
[hive-cluster 08:14:52] sync: light fast-forwarded 2914b4d612a3 target=cde8a92a3594
[hive-cluster 08:20:02] sync: light fast-forwarded 2914b4d612a3 target=cde8a92a3594
```

每轮还会对 `sync_cursor.json` 里 7–8 个仓各发一次 `ls-remote`（超时 15 s），这就是"启动后 git 一直在跑"的体感来源。**注意：本地 git 本身不慢**——`status --porcelain` 245 ms、`fetch --prune` 1.35 s。

### P2 git 子进程：编码与管道

`hive.py` 的 `run()` 早已钉死 UTF-8，但 `hive_repos._git_live` 还是 `text=True` 且不带 `encoding`。中文 Windows 的 locale 是 cp936，git 输出（提交信息、中文文件名）是 UTF-8：

```
Exception in thread Thread-7502 (_readerthread):
  File "C:\Python314\Lib\subprocess.py", line 1614, in _readerthread
    buffer.append(fh.read())
UnicodeDecodeError: 'gbk' codec can't decode byte 0xa5 in position 65
```

同一份日志里出现 **11 次**。更隐蔽的是第二个坑：`capture_output=True` 走 PIPE，git 拉起的后代（凭据管理器、`upload-pack`）会继承写端，`communicate()` 等不到 EOF 就永久阻塞——**timeout 只杀掉直接子进程，管道还被后代握着，调用照旧不返回**。这正是 `hive.py` 里 `_CaptureToFileProxy` 注释记录过的形态，但 `hive_repos.py` / `hive_cluster.py` 两处没跟上。

实测触发点：`C:\dswork\lighthive` 的 `origin` 是 `http://192.168.1.5:3000/skywalk/lighthive.git`，服务端直接 **401**，本机没有该 URL 的凭据：

```
$ GIT_TERMINAL_PROMPT=0 git -C lighthive ls-remote --heads origin     # 卡住 >12s 未返回
$ GIT_TERMINAL_PROMPT=0 git -c credential.helper= ls-remote …         # 0.34s 失败
fatal: could not read Username for 'http://192.168.1.5:3000': terminal prompts disabled
```

`GIT_TERMINAL_PROMPT=0` 挡的是终端提示，**挡不住凭据助手（GCM）**；GCM 在无界面会话里等一个永远不出现的输入框。`remote_head` 失败后 `fetch_if_changed` 会"回落无条件 fetch"，于是每轮多等 `HIVE_NET_TIMEOUT=120 s`。这就是"卡着"最直观的那段时间。

### P3 心跳线程池：每次新建

`_peer_heartbeat` 旧写法：

```python
with ThreadPoolExecutor(max_workers=min(8, len(peers))) as pool:
    futs = {pool.submit(http_json, …): p for p in peers}
```

心跳默认 1 s 一轮 × 3–5 个 peer，线程创建速率远高于回收。日志里：

```
维护循环异常（继续）：MemoryError()        × 31   （集中于 11-22 15:26、11-23 23:17、11-24 01:25–01:35）
心跳循环异常（继续）：RuntimeError("can't start new thread")  × 3
Exception ignored in thread started by … ThreadPoolExecutor-556_1
```

`hive_cluster.py` 里 11-23 的事故注释写得就是这条：hived 死于 `MemoryError` 后 `cluster.pid` 的号码被 `msedge.exe` 复用，`cluster start` 认为"在跑但没响应"，永不拉起。本次现场同样先看到 `检测到陈旧 pid：9460 已不存在`。

同一类问题还有 7 个调用点（`_sync_term_from_peers`、`_carrier_sense`、`_start_election`、`_leader_heartbeat`、`_peer_heartbeat`、`_replicate_op`、`_commit_op_replicated`），全部是"每次调用新建池"。

### P4 看板：pid 号码被复用，脚本只看号码

```
$ cat ~/.hive/run/dashboard.pid
1664
$ Get-CimInstance Win32_Process -Filter 'ProcessId=1664'
conhost.exe   start=11/24 07:20:49
```

`scripts/dashboard-service.cmd` 的 `:do_start` 只做 `Get-Process -Id $old` 就判定"已在运行"，于是：

```
dashboard already running (pid=1664), port 8787     ← 实际 8787 根本没监听
```

`hive cluster start` 里的 `dashboard_ensure(wait=3.0, force=True)` 又把异常 `pass` 掉，于是人只看到下一行"看板 未运行"，无从判断是启动脚本退出了还是端口没起来。

### P5 DuMate `0x10000002`：错误页来自 agt 被外部终止

错误页文案在 `resources/app.asar` 里与 `platform.onServiceUnexpectedExit` 绑定，码是服务退出时统一生成的：

```js
console.log("[App] Service unexpected exit:", e), I.report(e)
… 软件进程出现错误，请点击重启按钮尝试修复（错误码：0x10000002）…
```

对应日志（`log/electron.log`，该文件自 11-21 起）：

```
[2026-11-24 08:14:31.832] [error] [Dumate-agt] Unexpected exit with code 0 (possibly killed externally)
[2026-11-24 08:14:31.836] [info]  [Dumate-agt] Pid file cleared: …\log\opencode\opencode.pid
```

"exit code 0 + 外部结束"= 不是崩溃，是被父进程/作业对象终止。旁证：近 5 小时 Windows 事件日志 0 条 `1000/1001`、`crashDumps\electron-native\reports` 为空、`0x10000002` 在日志里只出现在用户消息里。时间点与本机发起的一轮重负载 pytest + 集群同步重合，属于资源压力下的进程回收；08:17 后端重启、08:18 起恢复正常。

### P7 `lightprism` diverged：工作副本停在任务分支

```bash

$ git -C lightprism log --oneline --stat origin/main..HEAD
```

## 5. 过程中自己引入又修掉的回归

第一版"`ahead`/`diverged` 终态跳过"只比较游标里的 `target`，导致人把仓修好之后状态仍被钉在 `diverged`（`lightprism` 归位后仍显示 diverged 就是这个）。修正为：跳过前先取**本地 HEAD 现况**，只有"远端未变且本地仍等于游标 sha"才跳过；命中 target 时连同 `sha`/`target` 一起刷新。改完编译、重启、复验通过。

教训：**终态优化必须带"现况指纹"**（这里就是 HEAD），否则会把人的修复也一并跳过。
