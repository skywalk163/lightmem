## 2. G8 修复（P0 越权读）——本线第一优先项

### 2.1 根因（E 线 0.88 实测复现，本线修复）

旧谓词（`backend_pg.go` `Query`/`VectorSearch` 同一写法）：

```sql
(visibility = $1 OR (visibility = 'shared_user' AND permission->'readers' ? $2) OR tenant_id = $3 OR $3 = ANY(shared_with_tenants))
```

两个独立缺陷：① `$1` 传 `q.Viewer`（用户名）却与 `visibility` 枚举比较 → **恒假**，owner 校验形同虚设；② `tenant_id = $3` **无差别放行** → `private` 行对同租户所有人（含**不传 viewer**）可见。SQLite/Qdrant 走 `canView` 本就正确，**仅 PG 分叉**，而 0.88 生产档正是 family+pgvector；既有 `TestSearchViewerPrivateIsolation` 跑在 SQLite 上，**永远测不到此分叉**（绿灯假象）。

### 2.2 修法（pre-filter，不动 Schema/migration）

新增 `pgVisibilityPredicate(viewerParam, tenantParam)`，**逐条对齐 `canView`**：

```sql
(
     (visibility = 'private'      AND user_id = $viewer AND $viewer <> '')
  OR (visibility = 'shared_user' AND $viewer <> '' AND (user_id = $viewer OR permission->'readers' ? $viewer))
  OR (visibility = 'tenant'      AND tenant_id = $tenant AND $tenant <> '')
  OR (visibility = 'cross_tenant' AND $tenant <> '' AND $tenant = ANY(shared_with_tenants))
)
```

`Query` 用 `$1/$2`（viewer/tenant），`VectorSearch` 用 `$2/$3`（`$1` 为向量、`LIMIT $4`）——参数重排后两处调用点同步更新。**空值守卫**（`$viewer <> ''` / `$tenant <> ''`）逐条对应 `canView` 的 `viewer != ""` / `tenant != ""` 前置条件，堵住「匿名 viewer 撞上空 user_id」的边角。

### 2.3 真机验证矩阵（0.88，PG 18.6，fresh 库 `lightmem_r21b`）

`TestPgVisibilityMatrix_G8Regression`（7 组查询，期望逐条对齐 canView）：

## 6. 遗留与交接（按责任方）

### 6.1 【C 线】handler 侧身份消费——G4 落库级闭环的唯一缺口

B 线机制（token→Identity→`ResolveActor`）已就绪且单测锁定；但 `handleToolSave`/`update`/`feedback`/`forget` 仍以 body `user_id` 为 actor（C 线文件域，本线不越权改）。**落地前 G4 的 handler 级冒充仍开放**（§4 末行实证）。C 线只需在四个 handler 的 actor 解析处把

```go
actor := m.UserID                       // 旧：信任 body
```

改为

```go
wid, _ := ResolveActor(r.Context(), m.UserID, m.TenantID)   // 新：token 优先
actor := wid.UserID
if wid.TenantID != "" { m.TenantID = wid.TenantID }
if err := EnforcePrivateOwner(r.Context(), m.UserID, string(m.Visibility)); err != nil {
    writeJSON(w, http.StatusForbidden, map[string]string{"error": err.Error()})
    return
}
```

（update/feedback/forget 同构：viewer 亦应从 `IdentityFromContext` 取。）落地后无需再动 B 线任何文件，§4 冒充探针预期即翻为「落库 `skywalk`」。

### 6.2 【收口/缺陷账】PG Upsert 的 `SharedWithTenants` 编码缺陷（新发现，R20 基线）

`stringArrFromJSON` 把 JSON 数组串（`["a"]`）直接当 `text[]` 字面量传参 → `malformed array literal`（SQLSTATE 22P02），**任何带 `SharedWithTenants` 的记忆在 PG 上写不进去**（0.88 实测；与 G8 无关，属 Upsert 参数编码）。本轮 PG 可见性测试用直连 SQL `$1::text[]` 补写绕开（`seedCrossTenant` 有注释）。建议列入缺陷账；修复点在 Upsert（JSON→PG array 转换），**不在 B 线谓词范围，本轮未动**。

### 6.3 【A 线】`cmd/lightmem-mcp` 独立二进制需挂 `AuthMiddleware`（任务书 A 线做法第 3 条）

装配示例见 `server_middleware.go` 追加段与 `main.go` 6b；`ConfigureAuth` 对 stdio 模式同样适用（token 走环境变量，stdio 无 HTTP 头则恒 401——stdio 场景建议不配置 token 走透传，或由部署层注入）。

### 6.4 【收口】`scripts/gate.sh` `[6]` 白名单条目（gate.sh:300）

需追加（测试函数数已实测达标）：`auth`（27）、`mcp`（18）、`workflow`（16，纯测试条目——无 `workflow.go`，gate 已有 test-only 通路）。`mcp_tools`/`mcp_tools_workflow`/`mcp_transport` 无同名 `_test.go`，由 A 线决定补测或申请 `name:threshold` 降档。

### 6.5 【收口/文档】`profiles/lims.profile.schema.json` 与 `profiles/README.md` 未动

auth 段的 JSON Schema 登记与 README 说明不在 B 线 yaml 文件域内，留待收口统一补（YAML 本身已被 `LoadProfileAuth` 独立解析，功能不受影响）。

### 6.6 【E 线 T3】生产部署

0.88 `:18443` 仍跑 R20 二进制（健康，pid 22190）。含 B 线（鉴权+G8 修复）与 A/C 线的生产部署、DSH 切原生 MCP、完整 `gate.sh`（PASS ≥14/FAIL 0）属 T3 收口动作。**部署前建议**：先配 `LIMS_AGENT_TOKENS`（或 profile auth 段）再暴露 18443——G8 已修但 G4 的 handler 侧（§6.1）落地前，写入面仍应默信内网。
