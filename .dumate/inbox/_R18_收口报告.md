## 四、合流期发现并修复的问题

### 4.1 【已修】B 线新文件未通过全仓 gofmt（门禁 [1b] FAIL）

- **现象**：首次跑门禁 `[1b] gofmt -l 全仓(严格)` **FAIL**，唯一文件是 B 线新增的
  `kernel/node_rpc_e2e_jail_test.go`。
- **定位**：`gofmt -d` 显示 gofmt 要把文件头那段大注释按 godoc 代码块规则**重排缩进为 Tab**
  （注释以 `//   R18 …` 起头且后续行有缩进，被当成代码块）。**不是**行尾问题（实测 CRLF=0）。
- **根因**：Windows 侧不能跑 `gofmt`（平台红线⑤），该文件缺一次 0.88 侧的格式化。
- **处置**：在 0.88 合流树执行 `gofmt -w kernel/node_rpc_e2e_jail_test.go`，并回写本机工作区；
  复跑门禁 **[1b] PASS（0 文件）**，全仓 gofmt 归零。
- **教训（已写入 R19 任务书 §七）**：凡新增 `.go` 文件，交付前必须在 0.88 跑 `gofmt -l` 归零。

### 4.2 【已核】任务书 §七-2 的测试路径有误

任务书写 `cd kernel && go test -count=1 ./eval/e2e/pg/...`，但 `eval/e2e/pg` 位于**根 module**
（`lightmem`），不在 `kernel/` 子 module 内。正确命令是在**仓库根**执行：

```sh
cd <repo-root> && go test -count=1 ./eval/e2e/pg/...
```

本轮已按正确路径执行并通过。建议在 R19 任务书中沿用正确写法（本报告即为准）。

### 4.3 【如实登记】A/B/D 未单独产出交付报告

任务书 §六 只要求「收口报告」为必备交付物，A/B/D 的**交付物本身齐全**（代码与文档均在树上），

## 五、偏差与需业主确认项

### 5.1 ⚠️ **红线①③：迁移 SQL 改动需业主确认**

- `kernel/migrations/001_pgvector.up.sql` 第 44 行：`confidence real` → `confidence double precision`（方案 a）。
- 任务书 §〇-1 与 §四 明确：该改动**触及红线①③，必须先业主裁定**。
- `lightmem.md` 新增 §D.8 记录「2026-10-16 业主裁定，允许触碰红线①③」。
- **本报告如实转述该记录，但合流者无法独立验证该裁定是否确实发生**；
  且 §D.8 同时声明**存量 float4 库本轮不执行 `ALTER`**，需另行维护窗口并按红线③再次裁定。
- **请业主确认**：若该裁定成立，本项关闭；若不成立，应回退该单行改动并改走方案 b（容差断言，零 SQL 改动）——
  经查 A 线**已同时落地方案 b 的 1e-6 容差断言**（`pg_e2e_test.go`），故即使回退方案 a，fresh 库与存量库断言仍可稳定通过。

### 5.2 B 线形态偏差：单机多监听替代「真·多 jail」

- 任务书 B 线验收原文要求「coordinator(lims-router:9443) + ≥2 worker jail 注册成功」。
- 实际交付为**单机多监听**：同一进程内启动 1 coordinator + 2 worker `NodeRPCServer`，
  各自监听真实随机 TCP 端口，走**真实 gRPC 协议**跨节点往返；覆盖注册/列表/心跳/`PurgeStale`/
  跨节点 `Query` 扇出/跨节点 `Revoke` 广播。
- 理由已写入手册 §11A.7.3.1：0.88 上既有 jail 已承载 PG/Qdrant，再塞 lightmem-k 有端口与数据冲突；
  cgo 二进制在 jail 内需逐 jail 预置；而 **jail vnet 传输层已由 R17 S1/S2 坐实**（0% loss + Qdrant 真机 HTTP）。
  故「多 jail」解决的是隔离/部署问题，与 B 线要验的「gRPC 应用逻辑」解耦。
- **判定**：作为**等效替代**接受，但**「真·多 jail」登记为后续可选项**（切换只需改三个 Start 地址 + pf 放行 9443，测试代码无需改动）。
- C 线据此在报告 §四.1 与 §七.1 如实标注：gRPC 档北极星复跑为**单节点回环口径**，真·多 jail 增量留待后续。

### 5.3 C 线口径边界（如实标注）

C 线报告已自陈：北极星复跑入口不装配节点注册中心（注册/心跳/扇出/撤销的接线在
`kernel/cmd/lightmem-kernel`，属 B 线文件域且不由评测入口触发）。因此 C 线的 gRPC 档验证的是
**「档位开关开启后北极星口径不降级」**，而非「多节点扇出对召回质量的增量」——后者由 B 线 3 个 `-race` 集成用例覆盖。
该边界不影响本轮「零降级」结论。

### 5.4 C 线「零代码改动」的等价实现

C 线因既有 `polaris_holdout.go`/`run_kpi.go` 硬编码 `{TierSolo, BackendSQLite}` 且无 `-profile` 参数，
在**复跑树内**建了纯运行 harness（6 个口径文件 byte-identical 副本 + 生成的 main），
仓库内**仅新增 2 个报告 JSON**。已核验 `git diff` 在 `eval/polaris/`、`rank_fusion.go`、`run_kpi.go` 为**空**，
符合「纯运行零改动」纪律（harness 仅存在于远端起跑树，属审计留档）。
