### 4.2 根因：融合链路缺「查询相关性信号」（关键结论）

统计基线报告的 top-1 输出（`details[].got`）：

- 530 次查询只产生 **133 个不同的 top-1 结果**；
- 单条记忆 `客户A的偏好是周一` 被 **32 次** 返回给互不相同的查询；
- 各桶 distinct top-1：single-hop 50/150、multi-hop 17/150、open-domain 43/100、temporal 48/130。

即 **top-1 基本与查询文本无关**。据此定位：

1. **`rank_fusion.default_weights.json` 是占位默认值**（任务书 §3.2 红线 4 要求标注「待 A8 校准」）。
2. **SQLite 骨架后端未接查询相关性信号**：BM25 全文检索与向量检索在该后端下未生效（§9/§4.2 已明确「全文检索需 BM25，PG tsvector 需自实现」），因此融合退化为一组**与查询无关**的信号（固有价值 / 时效新鲜度 / 来源可信度 / 反馈历史）排序，排序结果自然恒定。
3. **multi-hop = 0%** 有叠加原因：`run_kpi.go` 每条样本只物化 **hop-2（答案）** 记忆，hop-1（`客户A的决策人是谁`）仅存在于 `source_evidence.snippet`，文本/实体信号无从桥接，故必然检索不到。
4. **temporal = 0%**：`as_of` 过滤本身生效（写入的 `valid_from` 与查询 `as_of` 匹配），但因 (2) 无相关性信号，返回的仍是无关记忆。
5. **评测集自身的「同模板查询 / 多重可接受答案」退化（已修，见 v2 变更）**：
   初版 `genSingleHop`/`genOpenDomain`/`genTemporal`/`genTemporalChange`/`genMultiHop` 未把区分维度（day / decider / as_of / variant）嵌入 query 文本，导致**同一 query 文本对应多条不同 expected_fact**，使「同查询必返回同一 top-1」的评测口径下准确率被结构性封顶——**总体上限仅 34.0%**，远低于 §9 的 > 90% 目标。
   
   **v2 修法**：把区分维度写进问句——
   - `genSingleHop`：`客户A的偏好是什么（周一）`（嵌入 day）
   - `genMultiHop`：`客户A偏好什么时间开会（决策人：决策人001）`（嵌入 decider 名）
   - `genOpenDomain`：`给客户A准备什么方案（#01）`（嵌入 variant 编号）
   - `genTemporal`：`客户A偏好什么时间开会（2026-09-15 生效）`（嵌入 as_of 日期）
   - `genTemporalChange`：`客户A的预算是多少（2026-09-15 生效）`（嵌入 as_of 日期）
   
   修后 **530 条非对抗样本的 query 两两唯一**，口径上限恢复到 **100%**。

   | 分桶 | 条数 | 不同 query | 平均每 query 条数 | **口径上限** | 实测 |
   |---|---|---|---|---|---|
   | single-hop | 150 | 150 | 1.0 | **100%** | 1.3% |
   | multi-hop | 150 | 150 | 1.0 | **100%** | 0.0% |
   | open-domain | 100 | 100 | 1.0 | **100%** | 32.0% |
   | temporal | 130 | 130 | 1.0 | **100%** | 0.0% |
   | **总体** | **530** | **530** | 1.0 | **100%** | 6.4% |

   例：`客户A的偏好是什么（周一）` 唯一对应 `sh-000=客户A的偏好是周一`，不再与 `sh-050=…周二` / `sh-100=…周三` 冲突。**结论：评测集口径缺陷已修复，§9 的 > 90% 目标在修好评测集后结构上可达**。

> 因此 **6.6% 是「融合未接线」+「评测集退化」双重压制下的下限，既不是系统能力上限，也不是评测口径的合理基准**。任务书 §3.2 已预留「默认权重先占位、A8 出数后按评测结论校准」的机制，本轮 KPI 基线即该校准的**依据输入**。

### 4.3 建议的下一步（P3 范围，本轮不做）

1. **【最高优先】修评测集的口径退化（根因 5）**：让 `query` 文本携带区分维度（如 `客户A在 2026-10-11 的偏好是什么`，或把 `topic`/时间写进问句），使同一 query 唯一对应一条 `expected_fact`；修完上限才恢复到 100%，此前的所有准确率数字都不具备横向可比性。
2. 在 SQLite 后端接通 **BM25/关键词信号**，或在 KPI 评测中改用 PG 后端（pgvector + tsvector）复跑同一评测集，验证相关性信号接入后的跃升。

### 4.4 ⚠️ 本轮新发现（独立于 A1–A9）：KPI 基线**不可复现**（P0，已修）

| 运行 | 生成时间 | overall | open-domain | temporal | pollution_rate |
|---|---|---|---|---|---|
| **归档基线** | 01:02:44 | 6.6% | 24.0% | 0.0% | 5.0% |
| a9_verify 复跑 | 01:09:41 | 6.0% | 20.0% | 0.8% | 15.0% |
| 复跑 1 | 01:09:56 | 6.4% | 23.0% | 0.0% | 12.5% |
| 复跑 2 | 01:09:57 | 6.8% | 25.0% | 0.0% | 10.0% |
| 复跑 3 | 01:09:58 | 7.0% | 26.0% | 0.0% | 7.5% |

稳定不变的：`single-hop` 恒为 7.3%、`multi-hop` 恒为 0.0%、多信号融合恒为 0.0%。

**根因（已定位到行，v2 已修）**：候选集来自 `kernel/backend_sqlite.go` 对 `b.data` 这个 **Go map** 的直接遍历（`for _, m := range b.data`，见 `:97 / :142 / :168 / :207 / :230 / :250`）。**Go 的 map 迭代顺序是随机的**；在占位权重下大量候选**打分并列**，于是被随机顺序打散，top-1 随之抖动。

`rank_fusion.go:263`、`router_mem.go:264`、`backend_sqlite.go:123` 的比较器都**只按 score 排序，没有 `memory_id` 兜底**，无法消除这种抖动的传递。

**v2 修法（三处）**：
1. `backend_sqlite.go:Query`：比较器加 `memory_id` 次级键（`if a.Score == b.Score { return a.ID < b.ID }`）
2. `backend_sqlite.go:ScanLayer` / `ScanAll`：先全量收集再按 `(recorded_at, memory_id)` 排序，不可在 map 遍历中提前 break
3. `backend_sqlite.go:FindByIdempotencyKey`：命中多条时取 `memory_id` 最小者
4. `router_mem.go:RecallAndFuse`：仅当 `rf.Now` 未显式设置时才用当前时刻（`run_kpi.go` 固定 Now 避免逐条 freshness 抖动）
5. `run_kpi.go`：显式 `rf.Now = time.Now().UTC()` 固定评测启动时刻

**修后可复现性（0.88 实测）**：同一二进制连跑 8 次，总体准确率全部为 **6.4%**，分桶数字完全一致。

1. **降低无关信号（freshness/source_trust/feedback）+ 提升相关信号（entity/reference_frame）效果显著**
   - 总体从 6.4% → 18.7%（+192%）
   - open-domain 从 32% → 82%（+156%）

2. **提升 keyword/semantic 权重后，single-hop 和 open-domain 大幅跃升**
   - single-hop 从 1.3% → 29.3%（+22 倍）
   - open-domain 从 82% → 94%（+15%）

3. **multi-hop 物化 hop-1 后，从 0% → 100%**
   - 仅 1 行修改 + 1 个字段，效果立竿见影

4. **时序桶 0% 根因**：query 文本与事实文本不包含相同的区分性关键词
   - 原 query：`客户A偏好什么时间开会（2026-09-15 生效）`
   - 事实：`客户A偏好周一下午开会`
   - 重叠：客户, A, 偏好, 开会 = 4/10 = 40%
   - 开放域事实含"什么"，与 query 匹配 → 胜出
   - **方案 A 修法**：query 改为 `客户A偏好周一下午开会（2026-09-15 生效）`，与 fact 完全匹配

5. **排序确定性已修，调参不再被噪声干扰**
   - 3 次连跑完全一致
