## 2. A1 路：MemoryRouter 意图识别 + 跨层召回

### 2.1 目标

实现 `POST /mem/router`，输入一条查询文本 + 上下文（tenant/user/project/agent/scene/task），输出：

```json
{
  "intent": "query_knowledge" | "record_fact" | "confirm_preference" | "session_only",
  "recalled": [ {"layer": "L1", "candidates": [...], "count": 3}, ... ],
  "fusion_scores": null  // 未融合，交 A2
}
```

### 2.2 意图识别（不调 LLM，用规则）

- 输入含「记住/以后/别忘了/偏好是」→ `record_fact` / `confirm_preference`
- 输入含「查询/帮我找/有哪些/是什么」→ `query_knowledge`
- 输入仅为当前会话使用（无持久化意图）→ `session_only`
- 其他 → `query_knowledge`（默认）

规则表写成 `意图规则` 结构体数组，方便后续加规则，不写死 if-else 长链。

### 2.3 跨层召回

- 四层并行召回：L0（工作记忆，用 SQLite/pgvector 短时查询）、L1（动态）、L2（静态）、L3（归档，默认跳过除非 `include_archived=true`）。
- 每层 top-k（默认 k=5，可配）。
- 硬过滤先做：tenant/user/project/visibility（§3.2 安全硬过滤清单）。
- 输出未融合候选集，交给 A2。

## 3. A2 路：多信号 rank 融合引擎（主菜）

### 3.1 背景（§3.4 原文）

多信号独立打分（**不再用单一线性加权**）：

| 信号 | 实现 | 权重来源 |
|---|---|---|
| 语义相似度 | pgvector 向量检索 | 评测集校准 |
| 关键词匹配 | BM25（全文索引） | 评测集校准 |
| 实体匹配 | 实体链接/规范化 | 评测集校准 |
| 记忆固有价值 | §5.3 | 固定公式 |
| 时效新鲜度 | 指数衰减，半衰期可配 | 固定公式 |
| 来源可信度 | 人工 > 系统 > 用户 | 固定 |
| 参考系匹配度 | 上下文坐标匹配 | 评测集校准 |
| 反馈历史 | 采纳/弃用统计 | 固定 |

**融合机制**：各路信号先独立打分，再按名次（rank）融合（Reciprocal Rank Fusion 变体：`score = Σ 1/(k + rank_i)`），而非直接线性加权。

**融合策略（§3.4）**：
- 唯一最优：融合后名次最高者胜出。
- 接近融合：仅当 `(top1 - top2)/top1 < 20%` **且** `top1 ≥ 0.6`（绝对分下限）才融合多条；否则返回单条 + 标注低置信。
- 冲突标记：无法融合时保留多条，标 `requires_confirmation=true`，不静默选一个。
- 时效裁决（双时态）：默认只返回当前生效版本；`as_of` 回溯时返回覆盖时刻版本。

### 3.2 实现

新建 `kernel/rank_fusion.go`：
- `type SignalFunc func(ctx, query, candidates) map[string]float64` 各信号打分器接口。
- `type RankFusion struct { Signals []SignalFunc; Weights map[string]float64; AbsoluteFloor float64; ProximityRatio float64; HalfLife time.Duration }`。
- `Fuse(query, candidates) []FusedResult` 核心融合函数。

**权重校准**：默认权重先写入 `rank_fusion.default_weights.json`，标注「占位默认值，A8 KPI 出数后按评测结论校准」，**禁止无依据的固定先验写成"调优好"**。

### 3.3 单元测试

新建 `kernel/rank_fusion_test.go`，覆盖：
1. 单信号命中（唯一最优）。
2. 多信号 top1/top2 接近（<20%）且 top1 ≥ 0.6 → 融合多条。
3. top1 < 0.6 → 不融合，返回单条 + 低置信标记。
4. top1/top2 差距大（≥20%）→ 唯一最优。
5. 双时态：`as_of` 回溯返回历史版本，`is_historical=true`。
6. 冲突样本 → `requires_confirmation=true`。

## 4. A3 路：WritePolicy 插件注册表

### 4.1 目标

实现 §3.15 写策略插件，让新增写校验规则无需改动核心模块。

### 4.2 接口

```go
// kernel/writepolicy.go
type WritePolicy interface {
    Name() string
    Validate(ctx context.Context, m *Memory, meta WriteMeta) error  // 返回 error 即拒绝
}
type WritePolicyRegistry struct {
    policies map[string]WritePolicy
    order    []string  // 保证确定性执行顺序
}
func (r *WritePolicyRegistry) Register(p WritePolicy)
func (r *WritePolicyRegistry) Remove(name string)
func (r *WritePolicyRegistry) ValidateAll(ctx context.Context, m *Memory, meta WriteMeta) error
```

### 4.3 内置策略（本轮必装）

1. **GoalConstraintsPolicy**：`memory_kind=goal` 时校验 `goal_detail.constraints` 非空、KPI target > 0、status 合法。
2. **PermissionPolicy**：`permission` 三元组非空（owner 必填），`permission_level` 合法值。
3. **RedactionPolicy**：`fact` 命中敏感模式（如邮箱/手机号）时打 `permission_level=机密` 或脱敏（截断）。
4. **PoisoningGuardPolicy**（§7.5）：`provenance` 标记 `prompt_injection_suspect` 时，`confidence` 上限降为 0.3，且 `source_evidence.snippet` 截断到 200 字符。
5. **IdempotencyPolicy**：写入前查 `idempotency_key`，已存在则忽略（只增不覆盖）。

### 4.4 接线

在 `handleUpsert` 里，插入到幂等检查之后、写入存储之前调用 `registry.ValidateAll`（§4.5 幂等检查前置于 WritePolicy）。

## 5. A4 路：晋升/降级自动流转

### 5.1 背景

现有 `lifecycle.go` 有骨架，但可能是按时间硬晋升（不推荐，§3.1 原文「不按固定时间硬晋升」）。本轮改为**按固有价值分数自动流转**。

### 5.2 方案

- 固有价值分 = `0.5*importance + 0.3*recent_access_score + 0.2*confidence`（权重可配）。
- 阈值（默认，可配）：
  - L0 → L1：价值分 ≥ 0.6 或 access_count ≥ 3
  - L1 → L2：价值分 ≥ 0.8 且 稳定期 ≥ 7 天（无 feedback rejected）
  - L2 → L3：价值分 ≤ 0.3 或 valid_until 已过期
  - 降级 L2 → L1：价值分 < 0.5 且 无近期访问
- 后台 worker（与 A6 整合）每 N 分钟扫描一次，批量流转。
- **不物理删除**，只改 `layer` 字段，`version_history` 追加。

### 5.3 单测

新建 `kernel/lifecycle_test.go`，覆盖各阈值边界、不重复流转（同一记忆同轮只流转一次）、`version_history` 追加正确。

## 7. A6 路：后台整合 worker（consolidation）

### 7.1 目标

实现 §3.13 后台整合，定期执行：
1. **重复记忆合并**：同 `idempotency_key` 或同 `reference_frame_business_key` 的重复条目，取最新版，旧条目标 `superseded_by`。
2. **procedure 提炼**：同 scene+task 的多次成功 procedure 抽取，生成通用 procedure 记忆（本轮先做骨架，规则简单：同 scene+task 且 ≥3 次采纳 → 生成）。

## 8. A7 路：评测集建设（P2.5，可与 A1-A6 并行）

### 8.1 目标

按 LoCoMo 四类分桶建设评测集，≥ 500 条，含双时态变更 + 污染/投毒样本。

### 8.2 分桶设计

| 分桶 | 条数 | 定义 | 样例 |
|---|---|---|---|
| **单跳**（single-hop） | ≥ 150 | 单条记忆即可回答 | "客户A偏好周二开会" |
| **多跳**（multi-hop） | ≥ 150 | 需 2+ 条记忆链式推理 | "客户A的决策人是谁？" → 需 entity + preference 两条 |
| **开放域**（open-domain） | ≥ 100 | 无明确 schema，需开放推理 | "给客户B准备什么方案" |
| **时序**（temporal） | ≥ 100 | 双时态变更，需判断生效区间 | "客户A 2026-09 与 2026-10 的偏好变化" |

**跨桶附加样本**：
- 双时态变更样本：≥ 30 条（含 `valid_from/valid_until` 变更，需 `as_of` 回溯）。
- 污染样本（错误记忆写入）：≥ 20 条（`confidence` 低，应被拒/降权）。
- 投毒样本（prompt injection）：≥ 20 条（含指令性文本，`provenance=prompt_injection_suspect`）。

### 8.3 数据来源与生成

- **不允许用 LLM 生成答案**（避免污染指标）。
- 用 Go 脚本 `eval/eval_generate.go` 从模板 + 固定 seed 确定性生成（如 100 个实体 × 5 场景 × 若干事实），人工构造变更/污染/投毒样本。
- 输出 JSONL：`eval/dataset/{single,multi,open,temporal}.jsonl`，每条含：`id, query, expected_memory_ids[], expected_fact, bucket, is_temporal, has_injection, has_pollution, tenant, user, as_of（时序桶）`。
- 每条记忆对象用 `Memory` Schema，可直接写入 kernel 做检索。

### 8.4 交付

- `lightmem/eval/eval_generate.go`（生成脚本）
- `lightmem/eval/dataset/*.jsonl`（四类分桶 + 附加样本）
- `lightmem/eval/README.md`（分桶定义、加载方法、与 §9 KPI 映射）

## 9. A8 路：KPI 基线评测器

### 9.1 目标

### 9.2 评测器

新建 `lightmem/eval/run_kpi.go`：

2. 逐条构造记忆写入 kernel（走 WritePolicy）。
