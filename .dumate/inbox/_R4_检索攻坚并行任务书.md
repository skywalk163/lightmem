## 1. A 路 — multi-hop 原生检索能力落地（公开基准口径 A ≥ 0.95）

### A.0 范围与红线澄清

- **允许**：在 `kernel/` 新增 multi-hop 检索实现文件（如 `kernel/multihop.go`），在 `router_mem.go` 中**调用**；在 `eval/run_kpi.go` 新增 multi-hop 诊断 flag。
- **禁止**：改动 `Memory`/`RouterContext`/`RecalledCandidate` Schema 语义；用 LLM 做 hop 推理。
- **前置**：kernel/ 当前 grep "MultiHop|Hop1|hop" 仅 `embedder_tfidf_test.go` 命中——**kernel 无 multi-hop 原生检索**，评测器是手工物化 hop-1+hop-2 的。

### A.1 背景（根因，R3-D §4.3 + §6）

**R3-D §4.3**：公开基准 multi-hop 165 条中，口径 A 命中 156、top-2 命中但 top-1 未命中 6 条、top-2 内均未命中 3 条。

**R3-D §6**：口径 A 0.945 反映的是**真实检索排序能力**（156/165 = 94.5% 一次交互内拿到正确事实），hit@2 98.2%（162/165）说明**绝大多数是排序而非召回缺失**。**建议 P8 优化 multi-hop 场景的检索（如 hop 链式推理、上下文增强）。**

### A.2 目标

1. **kernel 层新增 multi-hop 原生检索能力**（不依赖评测器手工物化）。
2. **公开基准 multi-hop 口径 A ≥ 0.95**（当前 0.9455，差 0.0045）。
3. **hit@2 不回归**（≥ 0.982）。
4. **主 MRR 不回归**（≥ 0.9599）。
5. 其余桶（single-hop / temporal / open-domain）**不回归**。
6. 提供 isolate 验证（临时禁用新检索，复现 R3-D 基线 0.9455）。

### A.3 交付

1. **`kernel/multihop.go`（新增）**——multi-hop 检索能力：
   - **hop 链式推理**：以 query 的 `reference_frame.entity` / 关键实体为锚，先从 L1/L2 召回相关记忆（hop-1），从 hop-1 记忆的 `fact` / `context` 中提取新的查询锚点（如新的 entity、时间、数值），再二次召回（hop-2）。
   - **上下文增强**：对二次召回的候选做 context 聚合，构造「hop-1 → hop-2」的推理链，返回带链式来源的候选（如 `FusedResult.Reason = "multi-hop: <hop1_id> -> <hop2_id>"`）。
   - **确定性**：不用 LLM；用 char n-gram TF-IDF embedder（R3-A）做二次召回匹配；seed 无关。
   - **接口**：新增 `APIServer.RecallAndFuseMultiHop(ctx, rc)` 或在 `RecallAndFuse` 内检测 rc 标记后走 multi-hop 路径；**不动现有单跳路径行为**（单跳查询走原逻辑）。

2. **`kernel/router_mem.go`（修改）**：
   - 在 `RecallAndFuse` 中**检测**是否需要 multi-hop（如 rc.Text 含多跳语义标记，或 `rc.MemoryKinds` 含特定类型）；需时调用 `multihop.go` 的新路径。
   - **确保单跳路径行为逐位不变**（isolate 验证）。

3. **`eval/run_kpi.go`（修改）**：
   - 新增 `-no-multihop` flag（临时禁用 multi-hop 检索，用于 isolate 复现 R3-D 基线）。
   - 新增 `-hop-depth <n>` flag（hop 链式推理深度，默认 2）。
   - 新增 multi-hop 诊断 flag `-diag-mh <id>`：打印指定样本的 hop-1 → hop-2 链式召回轨迹。

4. **单测**：`kernel/multihop_test.go`（新增）——覆盖：
   - 单跳查询不触发 multi-hop 路径（行为不变）
   - 双跳查询能正确链式推理（构造两跳记忆，验证 hop-1 → hop-2）
   - hop 链式推理确定性（seed 无关，重跑结果一致）
   - 上下文增强能提升 top-1 命中（构造干扰项，验证聚合后命中）

5. **报告**：`eval/reports/multihop_native_<ts>.md`，含：
   - 公开基准 multi-hop 三口径（主 / 口径A / hit@2）before/after
   - **isolate 验证**：`-no-multihop` 复现 R3-D 基线 0.9455
   - 6 条 top-2 命中未达 top-1 的样本 before/after 逐条分析（是否被新检索修正）
   - 3 条召回缺失的样本 before/after 逐条分析
   - 其余桶不回归对照

### A.4 命令（0.88 上执行）

## 2. B 路 — reference_frame 变化评测集 + 合成集波动诊断 + as_of 默认开关

### B.0 范围与红线澄清

### B.1 背景（根因，R3-A §8 + R3-B §6）

**R3-A §8 风险表**：**reference_frame 信号无区分度**（公开集恒匹配、合成集恒空），非实现 bug，建议 P8 **构造带 reference_frame 变化的评测集**（不同 entity/project/task），或接受该信号在检索场景下无价值。

**R3-A §8 风险表**：合成集 fact 96.6% → 95.8%（−0.8pp）与合成集 top-1 68.3% → 67.5%（−0.8pp）波动。

**R3-B §6 决策**：`-now-asof` 默认 false（不开启），任务书/生产环境如需 as_of 时序一致性须显式传。

### B.2 目标

1. 构造带 reference_frame 变化的评测集（≥ 50 条），复检 reference_frame 信号区分度。
2. 合成集 fact/top-1 波动诊断出根因（isolate 实验）。
3. `-now-asof` 默认开启评估（公开/合成 MRR 不回归）。

### B.3 交付

1. **`eval/generate_reference_frame.go`（新增，`//go:build ignore`）**：
   - 构造参考系变化样本：同一 query 在不同 `reference_frame.entity` / `project` / `task` 下，期望命中不同记忆。
   - **生成方式**：从公开基准（LongMemEval/LoCoMo/BEAM）抽取真实样本，改写 `reference_frame` 坐标（纯模板替换，不调 LLM）；或从合成集模板扩展。
   - **确定性**：seed=42 固定采样；不用 `time.Now()`；不用 map 迭代序。
   - **输出**：`eval/dataset/reference_frame.jsonl`（或合并到 `all.jsonl` 新桶 `reference_frame`）。

2. **`eval/run_kpi.go`（修改）**：
   - 新增 `-now-asof-default` flag：默认开启 `-now-asof`（R3-B 后默认 false，此处评估开启的影响）。
   - 新增 `-diag-ref <id>` flag：打印指定样本的 `signalReferenceFrame` 打分与 QueryFrame 坐标。
   - 新增 reference_frame 桶统计（若评测集新增桶）。

3. **`eval/reports/reference_frame_<ts>.md`**：
   - reference_frame 变化评测集构造说明（样本数、变化维度、确定性）
   - reference_frame 信号复检：区分度（不同 reference_frame 下信号分变化）、有效性（权重搜索中是否重新进入变量）
   - 合成集 fact/top-1 波动诊断：isolate 实验（关闭 embedder / 恢复 R2 权重 / 恢复 freshness 旧行为）逐项定位根因
