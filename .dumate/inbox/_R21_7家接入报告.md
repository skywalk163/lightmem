## 2. 本轮新发现并修复的 4 个缺陷

| # | 缺陷 | 严重度 | 影响 | 处置 |
|---|---|---|---|---|
| **D-1** | **stdio 通道无身份**。stdio 没有请求头，二进制从 Windows 调 `0.88:18443` 属**非回环**，服务端不信任其 `X-Lightmem-*` → **全部 401** | **阻断** | CodeArts / Roo 完全不可用 | 新增 `SingleIdentity()`：stdio 场景**每个 Agent 各带自己那一条 token**，进程身份唯一确定；据此带 `Authorization` 并注入身份。**表内多于一条则拒绝**（不猜测，防错配） |
| **D-4** | Python 桥**不发 `Authorization`** | 高 | 启用鉴权后桥必 401 | 桥支持 `LIGHTMEM_AGENT_TOKEN(_FILE)` 并带头 |
| **新** | 桥的 `source` **硬编码 `deepseek-harness`** | 中 | 经桥写入的 CodeArts/Roo 记忆被**误标为 DSH 来源**，污染来源追溯 | 改为默认取本进程 `AGENT_ID` |

## 3. 一个意外收获：CodeArts 自己拉起了原生 MCP

操作期间发现 `lightmem-mcp.exe` 被**反复重生**，追父进程链得到：

```
CodeArts.exe  →  agent-kernel.exe  →  lightmem-mcp.exe -transport stdio -rest-base http://192.168.0.88:18443
```

即 **CodeArts 读到配置后主动 spawn 了我的原生 MCP 服务并保持连接**。
这比任何模拟都更有说服力：**配置已被真实客户端消费**。
（副作用：二进制被占用，需先停 CodeArts 才能替换 → 已在安装脚本中处理。）

### 3.1 为什么给 CodeArts/Roo 换成原生二进制

原先两家走 **Python 桥**，而桥只有 **7 个工具**——缺 `goal_create` / `goal_progress` /
`goal_state` / `plan_list` / `step_add` / `summary_add` 这 6 个**工作流工具**。
而「把工作计划/步骤/总结存进记忆」正是本项目的核心目标，**7 个工具等于功能残缺**。

**处置**：在 **0.88 上交叉编译** `GOOS=windows GOARCH=amd64`（仍在 FreeBSD 构建，
只换目标平台），产出 `lightmem-mcp.exe`，让这两家直接用原生 stdio —— 拿到与 HTTP
通道**完全一致的 13 个工具**，并去掉 Python 中间层。

### 9.2 顺带暴露出 G13（**T3 第 4 个新缺陷**）

**现象**（Trae 日志）：

```
22:25:16 [error] [mcp.config.usrlocalmcp.lightmem] MCPClient#onError
         streamable SSE stream disconnected: TypeError: terminated
22:27:44 同上   22:29:01 同上   22:31:41 同上
22:33:41 同上   22:36:08 同上   22:36:47 同上
```

**每约 1~2 分钟断一次**，随后反复重连。

**根因**：`GET /mcp` 是**长连接 SSE**（`handleGet` 里 30s 心跳、直到 `r.Context().Done()`），
但 `http.Server` 的 **`WriteTimeout: 120s` 覆盖的是整个 handler 生命周期**，到点即掐断。
断开间隔与 `WriteTimeout` **精确吻合**即为佐证。

**修复**：仅对 SSE 端点清除写超时（`http.NewResponseController(w).SetWriteDeadline(time.Time{})`），
保留全局 `WriteTimeout` 对普通 POST 请求的既有保护。

**验证**：

| 项 | 结果 |
|---|---|
| 长连接实测 | 稳定存活 **177.8s**（心跳 4 次），跨越旧的 120s 断点，未中断 |
| Trae 日志 | 修复部署（约 22:38）之后 **再无 `disconnected` 报错** |
| Trae token 端到端 | `tools/list` 13 工具 → `health` ok → `save` 成功 → `recall` 命中 |

> **教训**：Go 的 `http.Server.WriteTimeout` 对 **SSE / 长轮询**是陷阱 —— 它限制的不是
> "两次写之间的间隔"，而是**整个 handler 的墙钟时间**。任何长连接端点都必须显式清除
> 写超时，否则客户端会周期性断连，而**服务端日志毫无痕迹**（看起来一切正常）。
