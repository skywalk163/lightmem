## 1. A 路 — 注入确定性 embedder + 修复 reference_frame + 权重重校准 v2

### A.0 范围与红线澄清

- **允许**：在 `kernel/` 新增 embedder 实现文件（如 `kernel/embedder_tfidf.go`），实现 `RankFusion.SetEmbedder` 所接受的函数签名 `func(string) ([]float32, error)`。
- **允许**：修改 `kernel/rank_fusion.go` 中 `signalReferenceFrame` 的实现（**只改打分逻辑，不改字段语义**）。
- **禁止**：改动 `Memory` Schema、`RouterContext`、召回/写入链路语义。**禁止**用 LLM 做 embedding（红线 4）。
- **禁止**：改 `signalSemantic` 的 `embedder == nil` 退化分支（保留，供无 embedder 场景回退）。

### A.1 背景（根因，R2 收口报告 §7.1 + kernel 源码实测）

**R2 收口 §7.1**：评测器全程无 `SetEmbedder` 调用，`signalSemantic` 退化为 `RecallScore`，因此 A 路方案 α 只能跳过 semantic。**R3 必须走方案 β**：注入确定性 embedder，让 semantic 真正生效后再重跑权重搜索。

**R2 收口 §7.2**：`reference_frame` 被坐标下降压到 0.0（`rank_weights_en.json`），报告标注「P8 应排查 `signalReferenceFrame` 实现而非简单永久关闭」。

**kernel 源码实测（`kernel/rank_fusion.go`）**：

- `RankFusion.embedder` 字段（line 68）：`embedder func(string) ([]float32, error)`，`SetEmbedder` 方法（line 145）已存在。
- `signalSemantic`（line 465）：`if rf.embedder != nil && query != ""` 才走真实向量，否则退化 RecallScore。
- **`signalReferenceFrame`（line 627）**：
  ```go
  qf := rf.QueryFrame
  if qf == nil {
      for _, c := range cands { out[c.Memory.MemoryID] = 1.0 }  // ← 常数
      return out
  }
  // ... 收集 coords ...
  if len(coords) == 0 {
      for _, c := range cands { out[c.Memory.MemoryID] = 1.0 }  // ← 常数
      return out
  }
  ```
  → **当 `QueryFrame` 为空（评测器里未设置）或所有坐标字段都为空时，`signalReferenceFrame` 对每个候选都返回 1.0**。归一化后变成常数，`reference_frame` 权重乘常数对排序无影响。**这就是坐标下降把它压到 0.0 的直接原因**。

### A.2 目标

1. 为评测器注入一个**确定性、不调 LLM** 的 embedder（char n-gram TF-IDF 向量化），让 `signalSemantic` 真正生效。
2. **诊断并修复 `signalReferenceFrame`**：让它在 `QueryFrame` 为空时有合理降级（而不是返回常数 1.0），或明确记录「该信号在无参考系数据时无信息量」。
3. 重跑权重搜索（**semantic 重新进入搜索变量**，形成方案 β 搜索空间），输出 W_en_v2 权重。
4. 公开基准不回归（MRR ≥ 0.943），合成集不回归（MRR ≥ 0.831）。

### A.3 交付

     - 文本小写化，生成所有 **字符 n-gram**（建议 n=3，即 trigram；可选 n=2/3 双路）。

## 2. B 路 — temporal as_of 时序一致性 + freshness/feedback 确定性化

### B.0 范围与红线澄清

- **允许**：修改 `kernel/rank_fusion.go` 的 `signalFeedbackHistory`（把 `time.Now()` 换成 `rf.Now`）。
- **允许**：在 `eval/run_kpi.go` 加 `-now-asof` flag（实验用），把 `rf.Now` 设为样本 `as_of`。
- **禁止**：改动 `signalFreshness` 的衰减公式（保持指数衰减语义）；只改时间基准。
- **前置**：若 A 路已落地，基于 A 路的 `run_kpi.go` 二次修改；否则先单独修 `signalFeedbackHistory`。

### B.1 背景（根因，R2 收口报告 §8.2 + kernel 源码实测）

**R2 收口 §8.2**：`run_kpi.go` 固定 `rf.Now = 2026-10-12`，而 temporal 样本的 as_of 是 **2023/2024**。`signalFreshness` 用 `rf.Now - OccurredAt` 计算指数衰减，年龄 2-3 年 → `freshness ≈ 0`，归一化后变常数，**freshness 信号对 as_of 查询无区分度**。

**kernel 源码实测（`kernel/rank_fusion.go`）**：
- **`signalFeedbackHistory`（line 708）**：`now := time.Now().UTC()` ← **这里用的是真实当前时间，不是 `rf.Now`**。这是 R2 报告没发现的**第二个隐藏时间源**，导致：
  1. 违反 seed=42 确定性（每次评测反馈时间不同）。
  2. 与 as_of 时序不一致（as_of 是 2023 时，feedback 却用 2026 判断 90 天内是否近期）。
- **`signalFreshness`（line 589）**：用的是 `rf.Now`（正确），但 `rf.Now` 被固定为评测启动时刻，未跟随 as_of。

### B.2 目标

1. **修复 `signalFeedbackHistory` 确定性**：把 `time.Now().UTC()` 替换为 `rf.Now`（若 `rf.Now` 为零则回退 `time.Now().UTC()`，保持向后兼容）。
2. **实验 `rf.Now = as_of`**：as_of 查询时把 `rf.Now` 设为样本的 `as_of`，让 freshness/feedback 时序生效。
3. **验证**：`rf.Now = as_of` 时公开基准 MRR ≥ 0.943（不回归），temporal 桶 MRR ≥ 0.975。
4. 若 `rf.Now = as_of` 反而降级，**报告必须给出对照实验**（同 R2 B 路 §7.2 的方式），不强行采用。

### B.3 交付

   ```go
       now := rf.Now
       if now.IsZero() {
           now = time.Now().UTC() // 向后兼容：未显式设置时回退
       }

   ```
   > 注意：`rf.Now` 由 `eval/run_kpi.go:194` 在启动时固定；`signalFeedbackHistory` 之前忽略了它。**必须**把 `rf.Now` 设为评测启动时刻（与 `signalFreshness` 一致），再实验 as_of 变体。

2. **`eval/run_kpi.go`（加 `-now-asof` flag）**：
   ```go
   nowAsOf := flag.Bool("now-asof", false, "as_of 查询时把 rf.Now 设为样本的 as_of（R3-B 实验用）")
   ```

3. **报告**：`eval/reports/temporal_asof_now_<ts>.md`，含：

## 4. D 路 — multi-hop 口径 A 落地 + hit@2 辅助

### D.0 范围与红线澄清

- **前置**：R2 D 路已提出口径 A/B/C 建议，但未落地；R3 落地口径 A。

### D.1 背景（根因，R2 收口报告 §7.3 + D 路报告 §4）

**R2 收口 §7.3**：合成集 multi-hop MRR 恒 0.500，是样本设计 + rank 口径共同作用的结构性下限：
- 合成集 150 条 multi-hop：`ExpectedMemoryID = [hop2ID, hop1ID]`（`sample.go:105 toItems`）
- 评测器 `run_kpi.go:320`：top-1 命中 hop-2 → `j=0` → rank=1 → RR=1.0；命中 hop-1 → `j=1` → rank=2 → RR=0.5
- 因此**只要 top-1 召回的是 hop-1（中间跳板）而非目标 hop-2，MRR 只计 0.5**——这是结构性惩罚，不是检索能力缺陷。

**公开基准 multi-hop 165 条**：`ExpectedMemoryID` 通常是**单元素**（目标事实 ID），top-1 命中即 rank=1。

**R2 D 路 §5 已提出 3 种替代口径**：
- **口径 A（推荐）**：multi-hop 只要求 `top-1 MemoryID ∈ ExpectedMemoryID` 即算 hit（等价 rank=1），不区分 hop 顺序 → 可测「检索到目标事实集合」的能力，与公开基准可比。
- **口径 B**：`hit@2`（top-2 内命中任一 expected）。
- **口径 C**：保持现状但明确标注结构性下限。

**R3 任务**：落地**口径 A** 作为主指标，口径 B（hit@2）作为辅助；保留主 MRR 口径供历史对比。

### D.2 目标

1. 合成集 multi-hop 口径 A 下 MRR 与公开基准 multi-hop 口径 A 下 MRR **可比较**（不再是「0.500 结构性下限 vs 0.923 真实排序」的不可比局面）。
