## 二、A.2 只加不减融合模式（建议 2）

**文件**：`kernel/rank_fusion_monty.go`

**核心公式**（严格对齐 monty.md §4.3）：

```
evidence = clip(tolerance - diff, 0, ∞) / tolerance
```

| 输入 | 输出 | 语义 |
|---|---|---|
| `diff ≤ 0` | `1.0` | 完全匹配，取最大证据 |
| `0 < diff < tolerance` | `(tolerance-diff)/tolerance` | 容差内线性得分 |
| `diff ≥ tolerance` | `0` | **记 0，绝不记负分** |
| `tolerance ≤ 0` | `0` | 不做除零 |

**`FuseMonotonic(ctx, query, cands, cfg)`** 三条显式契约：

1. **只加不减**：每个信号只贡献 `∈[0,1]` 的正向证据；信号缺失或超容差记 `0`，**不产生负分**。
2. **相对容差**：`tolerance` 默认 `0.2`（与 §3.4 既有 20% 同量纲）；`diff > tolerance` **记 0 而非扣分**。
3. **保留绝对下限**：`top1 ≥ AbsoluteFloor`（优先沿用引擎 `rf.AbsoluteFloor`，缺省 0.6）为融合硬门槛，低于下限返回单条并标 `LowConfidence`——此约束为 lightmem 独有（Monty 无），按要求**明确保留**。

**分母口径**：融合分 = `Σ(w × evidence) / Σw`，分母只含**有信息**的信号权重——弱信号缺失既不稀释也不减分。

**差值口径**：默认 `relative`（`diff = 1 - 归一化分`，有界且与 §3.4 同量纲）；可选 `absolute`（原始分差），供调用方按信号量纲指定容差。

**输出**：`Ranked`（判决结果）+ `All`（**全量**候选逐条证据分，便于审计「为什么记 0」）+ `Evidences`（逐信号明细）。

**默认路径不变**：`RankFusion.Rank` / `Fuse` / `VoteFusion` / `rrfRank` / `consensusVoteRank` **零改动**，`FusionMode` 仍默认 `rrf`；`FuseMonotonic` 需调用方显式调用。

## 三、A.3 跨 Agent 参考系对齐前置（建议 5）

**文件**：`kernel/entity_align.go`

**`AlignCrossAgentFusion(ms, ref, policy)`** 两种模式：

| 模式 | 触发 | 语义 |
|---|---|---|
| **参考系模式**（跨 Agent 融合推荐） | `ref != nil` | 逐维与接收方参考系比对；不一致者进 `Unaligned` 并附差异维度说明 |
| **自分组模式** | `ref == nil` | 按各记忆自身坐标分组，同键同组；不同实体/场景天然隔离 |

**判定规则**（纯字符串、确定性、不调 LLM）：

- `entity` 缺失 → `AlignUnknown`（保守拒绝融合）；策略要求的 `scene`/`task` 缺失同理。
- 参考系模式下与 `ref` 任一要求维度归一化后不等 → `AlignUnaligned`。
- 归一化口径：小写、去标点与空白 → `"客户A"` 与 `" 客户a "` 视为同一实体。

**安全语义**：**未对齐只并列展示，禁止融合、禁止互相覆盖**；对齐失败降级为"待人工确认"，不静默放行。

**边界**：本函数**不参与、不放松**任何权限判定——`tenant/user/project/visibility` 硬过滤仍由既有 `canView` / 查询层负责（§3.2）；本函数只解决"都已可见之后**能不能融合**"。

**visibility 枚举核对（任务书 A.3 要求）**：`kernel/voting.go` 中**无** visibility 枚举，真源为 `kernel/model.go:21-26`（`VisPrivate` / `VisSharedUser` / `VisTenant` / `VisCrossTenant`），函数入参按该现状对齐，**未引入新枚举**。

**默认路径不调用**：`kernel/voting.go` 与 `kernel/rank_fusion.go` 均未改动。

## 七、R12 遗留缺陷修复（重要发现）

**根因**：R12 门禁的 `go vet ./...` / `go test ./kernel/` 在 **root module** 下执行，而 kernel 是**独立 module**（`kernel/go.mod` 自身为 `module github.com/lightmem/kernel`）。root 的 `go list ./...` 只匹配到 `lightmem/eval/polaris`，**kernel 包从未被真正 vet/test**——因此一批缺陷一路混进 main 且无人察觉。

**取证**：在纯净 R12 树（仅补 `net/http` 导入以解编译）复现出**完全相同**的 4 个失败，确认与 A 路改动无关。

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | `kernel/server_metrics_golden_test.go` 编译失败 | 缺 `net/http` 导入（`http.MethodGet` 等 18 处未定义）；另有 `bytes`/`fmt` 未使用 | 补 `net/http`、去未用导入 |
| 2 | 6 个基线 `.go` 文件 `gofmt -l` 非空 | 文件末尾缺换行符 | 补行尾换行（零语义） |
| 3 | `TestPrometheusTextGolden` 快照不匹配 | golden 期望按 path 排序，实际按完整 key 排序（`\|` > `/`）→ golden 基线记错 | `-update` 重生成 golden；二跑逐字节一致 |
| 4 | `TestPrometheusText_Compliance` 断言与输入不符 | 输入 5 请求断言 `_count 4`；输入 1 次 `/search` 断言 `recalled_total 2` | 断言修正为 `5` / `1` |
| 5 | `TestExtractPackageMemory_Idempotent` 幂等失效（`count 2 → 4`） | `pkgMemory` 每次生成新 `MemoryID`，SQLite `Upsert` 的幂等分支（同 ID + 同幂等键）永不命中 | 按代码库既有先例（`router_tools` 写入路径）先用 `IdempotencyLookup` 探测，命中则复用既有 `MemoryID`，使 Upsert 走 version 递增分支 |
| 6 | `TestPrometheusText_NoScientificNotation` 失败 | `formatFloat` 用 `'g'` 格式，1000000.001 → `"1.000000001e+06"`；Prometheus 文本格式禁用科学计数法 | 改用 `'f'` + 去尾零；**既有小数值输出逐字节不变** |

**复现命令**（供后续轮次复验）：

```bash

gofmt -l .                       # 期望：空
go vet ./                        # 期望：空
go test ./                       # 期望：ok

```

**给后续轮次的建议**：门禁应明确写为 **`cd kernel && go vet ./...` / `go test ./...`**（双 module 各自执行），否则 root 下 `./...` 的空跑会再次掩盖 kernel 缺陷。
