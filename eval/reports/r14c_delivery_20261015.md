## 二、C1 位移边持久化：`FileEdgePersistence`

R13 的 `EdgeStore` 只在进程内存里，重启即丢；C1 把位移边落到磁盘，
**但 `kernel/displacement_edge.go` 的既有符号语义一律不动**（只增新文件、新类型）。

### 2.1 接口

| 方法 | 语义 |
|---|---|
| `NewFileEdgePersistence(path, maxOut)` | 构造，**不触碰磁盘**；`maxOut <= 0` 回落 `DefaultMaxOutEdges`；构造期守卫（`TestEdgePersistConstructorGuards`） |
| `Load(ctx)` | 读文件 → `*EdgeStore`；文件不存在返回**空 store**（固定零时钟，`TestEdgePersistLoadMissingFile`）；损坏文件返回明确错误（`TestEdgePersistLoadCorruptFile`） |
| `Save(ctx, store)` | 序列化 → 原子写回；**重复 Save 逐字节一致**（`TestEdgePersistSaveIdempotentByteIdentical`） |
| `DDL()` | 建表语句文本（本实现不执行，见 §2.4） |

### 2.2 确定性：为什么"重复 Save 逐字节一致"

JSON 落盘最容易破确定性的三处，逐一堵住：

1. **无序**：`EdgeStore` 是 map，直接 marshal 顺序不确定。落盘前把边按
   **三元组字典序**（`from_memory_id` / `to_memory_id` / `relation`）输出
   （`TestEdgePersistFileStableOrder`）。
2. **时区**：同一边在本机 `Asia/Shanghai` 与 UTC 会序列化成不同字面量。
   序列化与反序列化**两端统一规整 UTC**，再以 unix 纳秒整数落盘，
   往返后 `UnixNano()` 逐位相同（`TestEdgePersistFileRoundTrip`）。
3. **尾随格式**：`json.MarshalIndent` + 固定缩进 + 固定尾随换行，无时间戳、无随机字段。

配合固定时钟（`edgePersistZeroClock`），空 store 与满 store 的往返都逐位可复现。

### 2.3 原子写回：同目录 `.tmp` + `os.Rename`

```go
tmp := p.path + ".tmp"
if err := os.WriteFile(tmp, buf, 0o644); err != nil { ... }
if err := os.Rename(tmp, p.path); err != nil {
    _ = os.Remove(tmp)   // rename 失败清理残留
    return err
}
```

- POSIX `rename()` 在同一文件系统内是**原子覆盖**：崩溃最坏情况是残留 `.tmp`，
  目标文件始终是完整旧内容，**不会半写**（`TestEdgePersistNoTmpLeftover`）。
- **Go 标准库没有 `os.Replace`**。初版误用了它，导致整个 kernel 模块
  `undefined: os.Replace` 无法编译——改用 `os.Rename` 修正。
- 目标目录不存在时先 `os.MkdirAll`，失败返回带路径的错误。

### 2.4 DDL：只增新表，绝不含 `ALTER`

SQLite 与 PostgreSQL 两套 DDL（`EdgePersistenceDDLSQLite` /
`EdgePersistenceDDLPostgres`），只建 `displacement_edges` 一张新表：

- `CHECK (relation IN ('entity-alias','causal','task-flow','temporal'))`
  与既有枚举契约一致；`CHECK (weight >= 0 AND weight <= 1)` 保住权重量纲。
- **三元组唯一索引是 partial index**（`WHERE invalidated_at IS NULL`）：
  软删行可累积、不占唯一性——符合"软删不物理删、保留审计"的契约，
  且同一对边可以在不同时间反复建删（`TestEdgePersistSoftDeletePreserved`）。
- 两条普通索引覆盖 from / to 两个方向的多跳遍历。

`TestEdgePersistDDLOnlyAdds` 的判定要点：先**剥离注释行**再扫描禁用词。
初版直接 `Contains("ALTER")`，把注释里的"禁止 ALTER"字样误判成改了既有表
——这是本轮自查出的**假阳性**，不是代码缺陷。

### 2.5 并发与容量

- `TestEdgePersistConcurrentSave`：并发 Save 不 panic、文件始终可解析。
- `TestEdgePersistMaxOutPreserved`：store 的 `maxOut` 覆盖持久化对象的缺省值，
  往返后容量上限不丢（否则重启后会用错容量上限做淘汰）。
- `TestEdgePersistSummaryCounts`：relation 计数与 store 摘要一致。
- `TestEdgePersistWeightPrecision`：权重浮点往返误差 `<= 1e-9`，
  JSON 序列化不改变权重量纲。
- 输出稳定性用例用**固定时钟**：若用递增时钟，建边顺序不同会让两个 store
  的 `created_at` 天然不同，用例必然失败、也测不出排序确定性。初版就踩过这个坑。

### 3.1 门禁挡住的三个假绿路径

1. **`go test` 必须带 `-count=1`**。不带时输出 `ok ... (cached)`，看着是绿的，
   实际一行测试都没跑。[4][5] 都强制带 `-count=1`。
2. **不能只跑根 module**。仓库是两个 module（根 `lightmem` + 子
   `github.com/lightmem/kernel`）。只跑根 module 时，kernel 的 `go vet` / `go test`
   **完全不会执行**，失败信息会以 `FAIL ... [build failed]` 出现在根 module 输出里，
   极易误判成"eval 目录的问题"。脚本自动发现所有 `go.mod` 并逐 module 执行。
3. **白名单必须逐文件 diff**。验证机的工作树是 tar 解压出来的、没有 `.git`，
   `git diff` 走不通。[7] 支持**目录基线**：`R14_BASELINE=/tmp/r13/lightmem sh scripts/gate.sh`，
   对每个受保护文件做 `diff -q`；没有基线时明确 SKIP，不做"假装检查过"。

### 3.2 [7] 白名单（12 文件，口径覆盖任务书 G8 的 10 文件）

任务书 G8 的 10 个受保护文件：`kernel/multihop.go`、`kernel/rank_fusion.go`、

`kernel/backend_pg.go`；另加 A / C 路自加的 `kernel/displacement_edge.go`、
`kernel/router.go`——共 **12 文件**，对 R13 基线逐文件 `diff -q` 一致。

`eval/holdout/holdout_v2.jsonl` 与 `eval/vectors/` 亦未改动
（`diff -rq` 显示仅 R14 工作树多 4 个生成脚本，向量数据本身相同）。

### 3.3 门禁自身的两个坑（已修，供后续复用）

| 坑 | 现象 | 修法 |
|---|---|---|
| BSD sed 的 BRE 不支持 `\+` | 版本号抽取为空，把 go1.25 误判成不达标（假 FAIL） | 改用 awk 做主/次版本比较 |
| [7] 在无 git 工作树上永远跳过 | 门禁矩阵看着 8 项齐全，红线检查形同虚设 | 支持目录基线，逐文件 `diff -q` |

另：脚本在验证机上必须先 `tr -d '\r'` 去 CRLF 再执行
（Windows 工作区写出的 `.sh` 是 CRLF，FreeBSD `sh` 会报 `\r: not found`）。
本仓库已用 `.gitattributes` 锁定 `*.sh text eol=lf`，检出即 LF。
