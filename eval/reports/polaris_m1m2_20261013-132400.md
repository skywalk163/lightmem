## 1. M1/M2 口径定义（分母分子说明）

### 1.1 M1 零 token 覆盖率（北极星主指标）

```
m1_coverage = hits / N
```

- **一次试验** = 一条 query 跑一次 `RecallAndFuse`。全程**无 LLM 生成调用**——
  「零 token」指答案由记忆检索直接给出，生成 token 消耗恒为 0（这正是北极星
  「低 token 长期运行」的经济性主张：检索命中即免生成）。
- **分子 hits**：expected 事实文本在 **top-K 候选 fact**（K=5，`-topk`）中被
  `matchFactV4` 判定命中。判定器从 `run_kpi.go`（R2→R5-B fact 口径链）逐位
  移植，见 `polaris_fact.go` 头部溯源说明——与 KPI 评测 fact 口径同源，
  「零 token 覆盖率」与「fact 准确率」可比。
- **分母 N**：计入的 query 数（对抗样本在代理语料生成时已剔除，见 §2）。
- 辅助口径：hit@1（top-1 即命中）、ID 命中率 / MeanRR（语料带
  `expected_memory_ids` 时；无 ID 语料的试验不计入该口径基数）。

### 1.2 M2 控制面 token 占比

```
m2 = Σcontrol_tokens / Σ(control_tokens + data_tokens)
```

- **控制面**：query + 路由 prompt + 召回 prompt 的表达 token（指令模板见
  `polaris_token.go`）。当前 Go kernel 编排是代码（0 token），指令模板是
  「prompt 表达口径」占位，用于与 Python+Prompt 基线同口径对比
  （定位文档 §7 M2 / §8.3 分离度量）。
- **数据面**：top-K 召回候选记忆正文（fact 文本）token。
- **token 估算**：确定性词元近似口径——CJK 单字 1 token、ASCII 词 1 token、
  标点不计；同输入逐位一致（无随机源），仅用于包内相对比较（压缩前后 /
  控制面数据面对比），非计费口径。
- 逐条 m2 比值的算术平均另输出（`mean_per_query_m2`）作对照。

## 5. 控制面光明语言压缩（实测数据）

### 5.1 压缩规则（`compress_light.go`，确定性）

R1 填充前缀剔除（请问/帮我/please tell me…）→ R2 句末语气词 → R3 句末疑问词/
系词（仅尾部，保护句中「是否」类意图词）→ R5 英文停用词（词边界，不含 a/an
防实体名误伤）→ R6 指令模板短化（自然语言长指令 → 光明语言短指令）。

**R4（的/了 文中剔除）已下线**——实验依据见 §5.3。

### 5.2 压缩前后对比（590 条 query）

| 指标 | 压缩前 | 压缩后 | 变化 |
|---|---|---|---|
| 控制面 token | 29050 | 18660 | **−10390（35.77%）** |
| M1 覆盖率 | 0.9661 | **0.9661** | **0（不降）** |
| hit@1 | 0.9559 | 0.9644 | +0.85pp（微升） |
| M2 控制面占比 | 0.4375 | 0.3447 | −9.3pp |

压缩率 35.77% ≥ 20% 验收线；覆盖率逐位不降（570/590 → 570/590）。
分桶覆盖率压缩后：single-hop 1.0 / multi-hop 1.0 / open-domain 1.0 /
temporal 1.0 / reference_frame 0.6667——**与基线完全一致**。

### 5.3 R4 下线实验（压缩规则迭代记录）

首版压缩含 R4（的/任何文中剔除），实测压缩率 37.42%、覆盖率 0.9661→**0.9542**
（−1.19pp，7 条单跳样本丢失）。丢失样本全是「客户A的偏好是什么（周三）」类
**带括号锚点**查询——删「的」后关键词信号减弱，top-1 翻到「周一」变体。
R4 只多贡献 1.65pp 压缩率却换来覆盖率有损，按「覆盖率不降」验收口径下线；
保守规则仍拿 35.77%。该决策已写入 `compress_light.go` 头部与单测
（`TestCompressQueryRules` 锁定锚点查询原样保留）。

## 6. 过程发现（重要，需收口跟进）

### 6.1 R5-B 重构数据集未入库（本轮踩坑与恢复）

- **现象**：D 路首跑北极星，multi-hop / temporal 两桶覆盖率 0.0。
- **根因**：`eval/dataset/*.jsonl` 全部停留在 R138-B 版本（`git log` 证实
  自 0575de1 起无提交）。R5-B 的 `eval_generate.go` 重构（multi-hop 单元素
  + query 内嵌桥梁事实「客户F偏好什么时间开会（决策人：决策人000）」）只在
  0.88 远端工作区落地，**其 commit（d6c7be7）不含 dataset 文件**；本轮到岗
  同步本地树时把远端重构版覆盖回 R138-B 旧版（旧版 query 无桥梁事实，
  hop-2 不可达 → 结构性 0.0）。
- **恢复**：按 B 路文档命令 `go run ./eval_generate.go -seed 42`（确定性）在
  0.88 复现数据集，重生成代理语料后复跑，各桶恢复 1.0。
- **isolate 证据**：同一代理语料（旧版数据集）下 `run_kpi.go` 与 polaris
  判定逐位一致（multi-hop 全 0）——0.0 是数据集版本伪影，非 polaris harness
  缺陷，也非检索回归。
- **建议收口**：把重构后的 `dataset/all.jsonl`（及 all_multihop_dual.jsonl）
  提交入库，或明确「数据集由生成器 seed=42 现生成」的基线口径；否则后续
  任何「本地→远端」同步都会重演本轮覆盖事故。
