## 三、A 路：参考系漂移衰减（monty.md §4.4 建议 3）

### A.1 依据与动机

- **Monty 痛点（反向借鉴）**：Monty 的 evidence 默认**无界累积、不遗忘**，其文档自承"换物体时旧证据应失效，有界更合理"。这是 Monty 的**缺陷**，我们反向吸收成一条显式规则。
- **lightmem 现状**：§5.3 已有固有价值与遗忘观测契约，`IntrinsicValue = 0.5*importance + 0.3*recent_access + 0.2*confidence`（`kernel/lifecycle.go:97`），衰减由**时间与访问**驱动；检索期已有 `signalReferenceFrame`（`kernel/rank_fusion.go:885`）与 `signalFreshness`（`:832`），但**没有把"参考系漂移"作为一等衰减维度**，也没有定义"很新但与查询参考系无关的记忆"如何快速下沉。
- **落点**：新增独立模块，不碰 `IntrinsicValue`、不碰默认 `RankFusion` 信号权重。

### A.2 交付物与接口

**新增** `kernel/forgetting_drift.go`（目标 250–350 行，纯函数为主，无全局状态）：

```go
// DriftAxis 三轴参考系维度（与 §3.2 ReferenceFrame 对齐）
type DriftAxis int // AxisEntity / AxisScene / AxisTask

// DriftConfig 衰减配置（全部可配，带默认值）
type DriftConfig struct {
    Axes        []DriftAxis      // 默认三轴全开
    HalfLife    time.Duration    // 半衰期，仅用于时间分量对照，不参与漂移判定
    Floor       float64          // 衰减地板，默认 0.15（防归零）
    Partial     float64          // 部分匹配系数，默认 0.6
    Neutral     float64          // 缺失视为中性，默认 1.0
}

// ReferenceDrift 单条记忆相对查询参考系的漂移因子，∈[0,1]
type ReferenceDrift struct {
    Factor   float64
    PerAxis  map[DriftAxis]float64
    Matched  []DriftAxis
    Missing  []DriftAxis
    Drifted  []DriftAxis
}

func DefaultDriftConfig() DriftConfig
func DriftOf(query *ReferenceFrame, mem *Memory, cfg DriftConfig) ReferenceDrift
func DriftAwareRank(ctx context.Context, query string, cands []RecalledCandidate,
                    cfg DriftConfig) []FusedResult   // 只加不减：仅乘性衰减，不加分
func DriftReport(d ReferenceDrift) string           // 审计文本，供 trace
```

**判定规则**（确定性、无随机、无字符串模糊匹配之外的启发）：

1. 轴内比对先做 R13 B 路同款归一化（小写、去标点、去空白），再判 `equal / partial / missing / drift`。
2. `equal → 1.0`；`partial → cfg.Partial`；`missing → cfg.Neutral`（**缺字段不算漂移**，避免误伤老数据）；`drift → cfg.Floor`。
3. `Factor = clamp(Π axes, cfg.Floor, 1.0)`，乘性而非平均，保证单轴漂移就足以下沉。
4. **只衰减不加分**：`DriftAwareRank` 在输入分数上乘 `Factor`，不引入新信号、不改权重、不进默认 RRF/consensus 路径。

### A.3 测试（`kernel/forgetting_drift_test.go`）

至少覆盖 12 项：三轴全等=1.0、单轴漂移=Floor、双轴漂移、全轴漂移、`missing` 走中性、空 `ReferenceFrame` 全中性、归一化等价命中、乘性单调性（漂移轴越多分越低且不低于 Floor）、`Partial` 生效、`DriftAwareRank` 结果确定性（打乱输入顺序输出一致）、`nil` 候选安全、**默认路径零改动断言**（同一输入下 `DefaultRankFusion().Fuse` 输出与 R13 基线逐位一致）。

## 四、B 路：显式 L0→L1 落库边界（monty.md §4.5 建议 4）

### B.1 依据与动机

- **Monty 依据**：buffer（STM）只存当前 episode，**episode 结束才 flush 进 LTM**——边界清晰，无中途脏写。
- **lightmem 现状**：§3.5/§3.13 是"持续捕获 → 压缩 → 整合"，L0（WorkingMemoryCache）到 L1（DynamicMemoryStore）的边界偏模糊；`SessionCompressor`（`kernel/goal.go:226`）只做压缩、不定义 flush 触发语义；`LifecycleScannerByValue`（`kernel/lifecycle.go:200`）按价值流转，与"何时该结算 L0"是两件事。
- **落点**：新增 flush 决策模块，**只产出计划不执行写**，执行仍走既有写入链路。

### B.2 交付物与接口

**新增** `kernel/flush.go`（目标 250–350 行）：

```go
// FlushReason 四类显式触发（§3.5.1）
type FlushReason int
const (
    FlushSessionEnd FlushReason = iota  // 会话结束
    FlushTopicSwitch                     // 话题切换
    FlushTaskDone                        // 任务完成
    FlushL0Capacity                      // L0 容量阈值
)

// FlushSignal 调用方传入的观测信号（不含写入权限）
type FlushSignal struct {
    Now         time.Time
    L0Count     int          // 当前 L0 记忆数
    L0Limit     int          // 容量阈值，默认 64
    TaskDone    bool         // 当前任务是否已完成
    SessionEnd  bool         // 会话是否已关闭
    PrevSnippet string       // 上一条记忆片段（话题指纹用）
    NewSnippet  string       // 拟写入片段
}

// FlushPlan 纯决策输出，不含执行
type FlushPlan struct {
    Flush     bool
    Reasons   []FlushReason
    Items     []string       // 需结算的 L0 memoryID，已去重排序
    HoldItems []string       // 留待下轮
}

func DefaultFlushConfig() FlushConfig          // L0Limit=64, TopicSwitchOverlap=0.35
func DecideFlush(sig FlushSignal, cfg FlushConfig) FlushPlan
func TopicFingerprintOverlap(a, b string) float64  // token 集合 Jaccard，确定性
```

**规则**：

1. 四触发**任一命中即 flush**，`Reasons` 按枚举序稳定输出；容量阈值用"≥ L0Limit"触发，防抖不留空转。
2. 话题切换判定用 `TopicFingerprintOverlap`（Jaccard 词集重叠）≤ 阈值 → 命中；**不依赖 R13 位移边**，保持 A/B/C 三路零跨路依赖。
3. **幂等**：同一 `FlushSignal` 重复调用产出同一 `FlushPlan`；`Items` 去重后按字典序，保证可断言。
4. **不执行写**：本模块不调用 `StorageBackend`，只返回计划；执行由调用方接既有 `Upsert`/生命周期链路。禁止在本文件新增任何写路径或 SQL。

### B.3 测试（`kernel/flush_test.go`）

至少覆盖 12 项：四类触发各自命中、无触发时不 flush、多触发并存且 `Reasons` 顺序稳定、`L0Count == L0Limit` 边界、重叠率恰等于阈值的边界、话题指纹对大小写/标点不敏感、幂等（重复调用同结果）、`Items` 去重与字典序、`nil`/空信号安全、`HoldsItems` 与 `Items` 不交、默认配置合理性断言、**既有 `SessionCompressor` 行为零改动断言**（同输入下输出与 R13 基线一致）。

`lightmem.md` 新增 **§3.5.1 显式 L0→L1 落库边界（v2.5）**，紧跟 §3.5 之后；必须画清"flush 决策"与"生命周期价值流转"的分工，避免读者以为二选一。**不删改 §3.5 任何既有结论。**

## 五、C 路：工程债收口（C1 位移边持久化 + C2 门禁固化）

### C1. 位移边持久化（R13 遗留 2）

R13 的 `EdgeStore` 是进程内内存实现，重启即丢。C1 补持久化，但**必须新增文件、不改 `kernel/displacement_edge.go` 的既有符号语义**。

**新增** `kernel/edge_persist.go`（目标 300–400 行）：

- **新表**（独立 DDL，禁止 ALTER 既有表/索引）：

```sql
-- SQLite
CREATE TABLE IF NOT EXISTS displacement_edges (
  id INTEGER PRIMARY KEY,
  from_memory_id TEXT NOT NULL, to_memory_id TEXT NOT NULL,
  relation TEXT NOT NULL, weight REAL NOT NULL,
  created_at INTEGER NOT NULL, invalidated_at INTEGER
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_disp_edge ON displacement_edges
  (from_memory_id, to_memory_id, relation) WHERE invalidated_at IS NULL;
```

- **接口**：`type EdgePersistence interface { Load(ctx) (*EdgeStore, error); Save(ctx, *EdgeStore) error }`；提供 `newSQLiteEdgePersistence`（真实往返）与 `pgEdgePersistence`（DDL 生成 + 接口实现，本轮**不接真机**）。
- **往返契约**：`Save` 后 `Load` 得到的 `EdgeStore` 必须满足——有效边数、软删边数、四类 relation 计数、权重逐条一致；软删行保留不物理删；重复 `Save` 幂等（不新增行）。
- **软删映射**：`invalidated_at` 与 `DisplacementEdge.InvalidatedAt` 严格双向对应。

**测试** `kernel/edge_persist_test.go`：SQLite 真实往返（建边→软删→Save→Load→逐条断言）、软删保留、幂等 Save、空 store 往返、relation 计数一致、权重浮点误差 ≤ 1e-9、并发 Save 不 panic、**既有表结构未被改动断言**（Save 前后对既有表 `PRAGMA table_info` 一致）。

**文档**：`lightmem.md` 新增 **§5.4.1 位移边持久化（v2.5）**，紧跟 §5.4 之后。
