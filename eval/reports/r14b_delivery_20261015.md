## 二、B.2 四类触发（`FlushReason`）

| 枚举 | 触发条件 | 说明 |
|---|---|---|
| `FlushSessionEnd` | `sig.SessionEnd == true` | 会话关闭，整批结算 |
| `FlushTopicSwitch` | 话题指纹重叠度 `<= TopicSwitchOverlap`（默认 0.35） | 新片段与上一条碎片化，旧话题该收口 |
| `FlushTaskDone` | `sig.TaskDone == true` | 当前任务完成，工作记忆可结算 |
| `FlushL0Capacity` | `L0Count >= L0Limit`（默认 64） | 容量阈值，防工作记忆无限膨胀 |

**默认值**（`DefaultFlushConfig()`，保守缺省，先定后调）：
`L0Limit = 64`、`TopicSwitchOverlap = 0.35`、`KeepRecent = 3`。
`sig.L0Limit > 0` 时覆盖 `cfg.L0Limit`（按调用现场调容量，不改全局配置）。

**话题指纹**（`TopicFingerprintOverlap`）：
对两条片段做分词（`flushTokens`）后取 Jaccard 重叠度；分词不区分大小写，
任一侧为空串即不触发（`TestFlushSnippetEmptyNotTrigger`）。重叠度 `<= 阈值` 才触发，
避免"稍有措辞差异就算换话题"的过冲。

## 三、纯决策契约（B 路最重要的一条）

`DecideFlush(sig, cfg) FlushPlan` 只产出**决策结果**，不执行任何写入：

1. **不碰 `StorageBackend`**：本文件 import 里没有任何存储后端符号，
   不写 `Memory`、不更新 `vector_status`、不产生审计行——
   因此不触碰 §4.2 的"元数据为事实源、向量异步补全"骨架。
2. **无 I/O、无网络、无磁盘**：决策只依赖入参 `FlushSignal`。
3. **无随机、无时间读取**：`sig.Now` 由调用方**注入**（便于确定性测试，
   本决策不使用它，仅供上层记录观测时刻）。
4. **可重复调用**：同一 `sig` 多次调用返回逐位相同的 `FlushPlan`
   （`TestFlushIdempotent`），因此可以放心"试算"而不产生副作用。

**`FlushPlan` 输出契约**：

| 字段 | 契约 |
|---|---|
| `Flush` | 是否结算（任一触发为真即结算） |
| `Reasons` | 触发的原因，**按枚举序稳定输出、无重复**（`TestFlushMultiReasonsOrder`） |
| `Items` | 本轮结算项：**去重 + 字典序**；空输入返回**非 nil 空切片**（`TestFlushEmptyItemsNonNil`） |
| `HoldItems` | 留待下轮，**仅**话题切换且 `KeepRecent > 0` 时非空；取输入顺序**尾部** N 条，输出按字典序；**与 `Items` 不相交**（`TestFlushHoldItemsAndItemsDisjoint`） |

`HoldItems` 的设计意图：话题刚切换时，最近几条往往还是旧话题的尾巴
（结论、引用、附件），一并结算会把上下文切得难看——留 N 条到下一轮，
与 `Items` 严格不相交保证**不重复结算、不丢条**。

**边界与安全**：

- `L0Count` 恰好等于阈值即触发（`TestFlushL0CapacityBoundary`）。
- `KeepRecent >= L0Count` 时全部进入 `HoldItems`（`TestFlushKeepRecentGECount`）。
- `KeepRecent < 0` 视为 0（`TestFlushNegativeKeepRecent`）。
- `sig == nil` 或 `sig.Items == nil` 均安全返回，不 panic（`TestFlushNilOrEmptySignalSafe`）。
- 未触发时 `Flush = false` 且 `Reasons` 为空（`TestFlushNoTrigger`）。

## 五、未覆盖项（留 R15）

1. **本轮无人调用**：B 路是纯策略模块，接入点（会话结束 hook / 写入前置检查）
   尚未接，因为接入即意味着定义"结算后 L0 条目变成什么"（L1 的 `recorded_at`、
   `memory_kind` 映射、是否需要再压缩一遍），这是 §3.5 与 §3.13 的语义合并，
   风险高于本轮收益。
2. **`SessionCompressor` 与 flush 的关系未统一**：`goal.go` 的压缩器目前只做
   "压缩"，不做"何时结算"。接入时建议把 `DecideFlush` 放在压缩**之前**：
   先决定要不要结算，再决定结算的东西怎么压。
3. **容量阈值 64 是缺省值，未做压测标定**：真实工作记忆规模分布未知，
   接入后应先观测再调。
