## 2. 背景与根因（R3-D §4.3 / §6）

R3-D 已定位：公开基准 165 条 multi-hop 中 **口径 A 命中 156**、**top-2 命中但 top-1 未命中 6 条**、**top-2 内均未命中 3 条**，并判定「差距是真实检索排序能力，不是结构约束，建议 P8 做 hop 链式推理 / 上下文增强」。

本次逐样本诊断（`-diag-mh`）确认了失败形态：

- **LME（LongMemEval）5 条**：目标记忆的 `fact` 本身就是 `question => answer` 卡片，**query 是它的字面前缀**；但融合分更高的「同题异构干扰卡」（如 `How much money did I raise in total through all the charity events I participated in? => $5,850`）被排到 top-1。→ **排序问题**，可用确定性证据纠正。
- **LoCoMo 4 条**：答案是跨轮对话推断，目标 turn 与 query 无字面桥接；其中 2 条目标压根未进 top-5（rank 13 / 17，真召回缺失），另 2 条覆盖率与干扰 turn 完全并列（0.20 / 0.22）。→ **现有 char n-gram 词面证据无法区分**，非本轮算法可解。

## 3. 实现

### 3.1 新增 `kernel/multihop.go`

在 A2（多信号 rank 融合）之后叠一层 **hop 证据重排**，三级证据：

| 级别 | 名称 | 判据 | 默认 |
|---|---|---|---|
| L1 | 直接回答 | 候选 `Fact` 归一化（小写 + 空白压缩）后**完整包含** query → 该记忆就是这道问题的答案卡 | 启用 |
| L2 | 锚点覆盖 | `|query 内容词锚点 ∩ 候选切分词| / |锚点|`；分词复用 kernel 既有 `tokenize`（ASCII 词 + 汉字单字/二元组），剔除功能词 | 启用 |
| L3 | 上下文增强 | 同参考系（tenant+user+scene）且时间窗内的 hop-2 邻接记忆，用其事实文本补强该候选的锚点覆盖，并写推理链 `Reason = "multi-hop: <hop1_id> -> <hop2_id>"` | **关闭**（`Depth>=2` 才启用，见 §4.3） |

排序键为全序 `(L1 desc, L2/L3 desc, 原融合序)`，用 `sort.SliceStable` 保证同键保留原序——**这是「不回归」的关键**：只有当某候选的证据严格更强时才会被提前。

关键 API：

```go
type MultiHopConfig struct{ Enabled bool; Depth int; ContextWindow time.Duration; MinAnchors int }
func DefaultMultiHopConfig() MultiHopConfig      // 默认 Enabled=false → 逐位兼容既有行为
func MultiHopReRank(query string, fused []FusedResult, cfg MultiHopConfig) []FusedResult
func MultiHopRankKey(query string, f FusedResult, anchors []string) (bool, float64)
func HopAnchors(query string) []string            // 去停用词后按字典序排序（确定性）
func (s *APIServer) SetMultiHopConfig(cfg MultiHopConfig)
func (s *APIServer) RecallAndFuseMultiHop(ctx, rc) (RouterResult, error)
```

确定性红线：不调 LLM；不使用 `time.Now()`；锚点集合显式 `sort.Strings`（不依赖 map 迭代序）；L3 按切片原序遍历取值（同增益取先出现者）。

### 3.2 `kernel/router_mem.go`（改）

`RecallAndFuse` 内 A2 融合之后增加 3 行：

```go
if s.multiHop.Enabled {
    fused = MultiHopReRank(rc.Text, fused, s.multiHop)
}
res.Fused = fused
```

**默认 `Enabled=false`，单跳路径逐位不变**；trace 里的 `Ranked` 由同一 `fused` 变量构建，因此诊断与统计口径自动跟随新序。

### 3.3 `kernel/router.go`（改）

新增 `multiHop MultiHopConfig` 字段（零值 = 默认关闭）。

### 3.4 `eval/run_kpi.go`（改）

| flag | 默认 | 语义 |
|---|---|---|
| `-no-multihop` | false | 关闭二次 hop 证据重排 → **isolate 复现 R3-D 基线** |
| `-hop-depth` | **1** | `>=2` 追加 L3 上下文增强（默认 1 的理由见 §4.3） |
| `-diag-mh` | "" | 指定样本 id（逗号分隔多个），打印 hop 锚点 + top-5 候选的 `answers/cover/hop-2 链/exp` |

### 3.5 新增 `kernel/multihop_test.go`（4 例，全 PASS）

1. `TestMultiHopReRankSingleHopUnchanged`——默认关闭 / 单候选时原序与 Reason 逐位不变；
2. `TestMultiHopReRankDirectAnswer`——融合分更低的答案卡被 L1 证据提到 top-1（复现 lme-d851d5ba 形态）；
3. `TestMultiHopReRankDeterministic`——同输入重复 50 次，ID+Reason 逐位一致；
4. `TestMultiHopReRankContextAugment`——L3 只在同参考系 + 时间窗内拼链，跨场景/ Depth=1 均不生效。

### 4.3 为什么 `-hop-depth` 默认 1（L3 上下文增强默认关闭）

L3 是任务书明确要求的机制，已实现并有单测覆盖，但**双源实测为负收益**，故默认关闭、保留开关：

| 配置 | 公开 口径 A | 公开 hit@2 | 公开 open-domain | 公开 temporal |
|---|---|---|---|---|
| depth=1（默认） | **0.9758** | **0.9818** | **0.9176** | **1.0000** |
| depth=2（30 天窗） | 0.9758 | 0.9818 | 0.9030 ⚠️ | 0.9878 ⚠️ |
| depth=2（7 / 30 / 90 天窗，离线扫描） | 0.9636~0.9758 | 0.9697~0.9818 | 0.9119~0.9331 | — |

结论：**增益全部来自 L1/L2（候选自身对 query 的回答性）；L3 邻接拼接在 LoCoMo 多轮对话场景下会把「时间相邻但主题无关」的 turn 拉高，反而伤 open-domain 与 temporal**。该结论已写进 `kernel/multihop.go` 的 `Depth` 字段注释，供 P8 决策是否重开。
